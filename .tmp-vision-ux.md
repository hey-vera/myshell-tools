## 1. CURRENT RENDERING MAP (what extends cleanly to MANY goals)

### The MVU spine
- **state.ts** — `UiState { committed[], goals: GoalView[], stream, turnActive, tokens }`
  (state.ts:143). `GoalView { id, label, state, tokens, agents: AgentView[], tier, risk? }`
  (state.ts:64). `AgentRunState = queued|running|done|failed` (state.ts:52) — **already
  has `queued`**, which is the key enabler for a multi-goal queue. `AgentView` has
  `provider/model/state/tokens/attempt` (state.ts:55).
- **reduce.ts** — pure folder. Goals are appended one-per-`tier-start` **only when NOT in
  panel mode** (reduce.ts:223-238). Sequential turns own exactly ONE running goal at a
  time; `settleActiveGoal` (reduce.ts:62) flips the *last running* goal at each tier
  boundary; `settleAllRunningGoals` (reduce.ts:98) belt-and-suspenders at `turn/final`.
  Tokens accumulate turn+session at every `flush-tier` (reduce.ts:344, 360).
- **core-event.ts** — pure CoreEvent→Action map (coreEventToActions, core-event.ts:34).
- **run-stream.ts** — `renderStreamInk` drives the event loop, dispatching into the store.
- **mount.tsx** — the ONE persistent `InkStore` (mount.tsx:92); `dispatch` folds + pushes.
  OutputSink chrome → `commit/raw` (mount.tsx:127). `turn/start` (mount.tsx:376) resets only
  the per-turn slice; `committed[]` only ever GROWS (the `<Static>` append-only contract).

### The view + cap
- **layout.ts** — PURE planner. `layoutForHeight(state, rows, streamLines, inputRows)`
  (layout.ts:290) proves `plannedRows + inputRows <= rows`. Degradation tiers
  (layout.ts:271-279): **full** cards → **compact** one-line summary → **hidden**. Row
  model: `PANEL_BORDER_ROWS=2`, per card `goalCardRows = 1 + agents.length` (layout.ts:167),
  `SUMMARY_LINE_ROWS=1`, `STATUS_LINE_ROWS=1`, `SAFETY_MARGIN_ROWS=1`, `INPUT_ROWS_MAX=12`.
  `summarizeTurn` (layout.ts:215) builds `▸ N goals/phases · M agents · tok · Ns`;
  `compactGoalsSummary` (layout.ts:234) builds the running/queued/done breakdown;
  `goalsAreSequentialPhases` (layout.ts:197) = all goals share one label → "phases" vs
  "goals" (honesty gate).
- **StatusBlock.tsx** — strictly paints the plan. `Panels` (StatusBlock.tsx:247) →
  `GoalCard` per goal (StatusBlock.tsx:201) → `AgentRow` (StatusBlock.tsx:139). `stateGlyph`
  (StatusBlock.tsx:45): queued ○ · running ◐ · done ✓ · failed ✗ — **already present**.
  `StatusLine` (StatusBlock.tsx:290) is the spinner verb. One animation owner; clock injected.

### Confirm/question machinery that ALREADY EXISTS (reuse, do not rebuild)
- **App.tsx `readKey()`** (App.tsx:126, impl 201) — read exactly ONE key through Ink's own
  pipeline; `<KeyCapture>` (App.tsx:375) consumes it; `awaitingKey` gates the InputBox
  inactive. `normalizeInkKey` (App.tsx:329) maps to legacy `readSingleKey` shapes.
- **menu-key-confirm.ts** — `confirmViaInkKey` (line 301) / `makeConfirm` (line 256) /
  `readMenuKey` (line 190) already drive single-key **y/n** + Enter-default + Ctrl-C→SIGINT
  via `inkReadKey`. `interpretYesNoKey` is the pure decision core.
- **menu-question-flow.ts `runQuestionSelector`** (line 38) — renders a numbered picker and
  collects answers; today `final.questions` sets `hasQuestions` which SUPPRESSES the
  completion line (reduce.ts:502) and the caller drives the selector. **This is exactly the
  pattern the "edit the plan" branch reuses.**

### Verdict — what extends cleanly
- **Multi-goal**: `goals: GoalView[]` is ALREADY a list; `AgentRunState` ALREADY has
  `queued`; `summarizeTurn`/`compactGoalsSummary` ALREADY count running/queued/done. The
  blockers are: (a) reduce.ts only ever has ONE running goal (sequential mirror), (b) no
  per-goal PHASE field, (c) layout.ts has no per-goal collapse — it's all-or-nothing
  (full → single compact line → hidden). These are additive.
- **Confirm**: the single-key + suppress-completion + selector pattern is all present. The
  plan-proposal just needs (a) a place in the live region to render, (b) one `readKey` y/e/n
  loop, (c) an edit path that reuses `runQuestionSelector` OR the InputBox.

## 2. CONFIRM-THE-PLAN UI DESIGN

### Where the plan renders
A proposed plan is **transient and editable**, so it must NOT go into `<Static>` (append-only;
can't be un-drawn if the user edits). It renders in the **live region** as a new bordered
panel ABOVE the StatusBlock GOALS panel, driven by a new `UiState.proposal` slice and a new
`layoutForHeight` row budget line. On accept it is **committed once** as a `raw` recap line
(`▸ Plan: 3 goals · accepted`) into `<Static>`, then execution begins and the proposal slice
clears. On reject it commits `■ Plan declined` and clears. This keeps `<Static>` monotonic.

### The flow (where it slots in the turn lifecycle)
The partner runs an **understand → propose → confirm → execute** cycle. The propose+confirm
happens BEFORE `renderStreamInk` starts the execution stream. Concretely in the menu loop
(the `runChatLoop` driver that already wraps mount.tsx:376 `turn/start` + run-stream):

```
1. user submits a message
2. partner classifies + drafts a PLAN (a new lightweight core call OR the intent/engagement
   frame already emitted — reuse CoreEvent 'intent'/'engagement', see types.ts:606/615)
3. dispatch { type: 'plan/propose', plan } → live PlanPanel renders
4. const verdict = await confirmPlanViaKey(out, bridge.readKey)   // y / e / n, reuses readKey
5a. y → dispatch { type: 'plan/accept' }; commit recap; turn/start; renderStreamInk(...)
5b. e → runQuestionSelector OR free-text InputBox edit; loop back to 3 with the revised plan
5c. n → dispatch { type: 'plan/decline' }; commit '■ Plan declined'; back to prompt
```

`confirmPlanViaKey` is a tiny variant of `confirmViaInkKey` (menu-key-confirm.ts:301): same
`out.flush()` + `readKey()` loop, but the decision core returns `yes | edit | no | ignore |
abort` instead of yes/no. Add `interpretPlanKey(key, default='yes')` next to
`interpretYesNoKey` in menu-questions.ts.

### ASCII mockup — the confirm step

```
╭─ PLAN ─────────────────────────────────────────────────────────╮
│ I'll do this in 3 goals:                                        │
│   1. Refactor the auth middleware        ic · medium            │
│   2. Add integration tests for /login    worker · low           │
│   3. Update the API docs                 worker · low           │
│                                                                  │
│ ~3 agents · est. medium effort                                  │
╰──────────────────────────────────────────────────────────────────╯
  Sound good?  [y]es  ·  [e]dit  ·  [n]o          (Enter = yes)
```

After pressing **e** (edit) — reuse `runQuestionSelector` to pick WHAT to change, then the
InputBox for the new text:

```
╭─ EDIT PLAN ────────────────────────────────────────────────────╮
│ What would you like to change?                                  │
│   [1] Goal 1 — Refactor the auth middleware                     │
│   [2] Goal 2 — Add integration tests for /login                 │
│   [3] Goal 3 — Update the API docs                              │
│   [4] Add a goal                                                 │
│   [5] Remove a goal                                              │
│   [6] Reorder                                                    │
│   [Enter] done — re-show the plan                               │
╰──────────────────────────────────────────────────────────────────╯
  Pick one, or Enter to go back:
```

Picking `[1]` drops to the live InputBox pre-seeded with the goal text (InputBox already
supports a history seed / current line). On Enter it loops back to the PLAN panel (step 3).

### Transition into execution
On **y**, the PlanPanel slice clears, a one-line recap commits to `<Static>`
(`▸ Plan accepted · 3 goals`), and the existing `turn/start` → `renderStreamInk` path runs —
**except** now the engine emits `tier-start` events carrying a `goalId` so each of the 3 goals
becomes its own running card (see §3/§4). The confirm step is purely additive: a turn with no
plan (trivial/streaming) skips `plan/propose` entirely and behaves exactly as today.

## 3. MULTI-GOAL PROGRESS VIEW DESIGN

### The shape
Today `goals[]` is a list but the reducer keeps exactly one `running`. The multi-goal view
keeps the SAME `GoalView[]`, adds a `phase {current,total}` field, and lets MANY goals be
`running`/`queued` simultaneously. Each goal card gains a **phase indicator**.

### Per-goal card (running, expanded)
```
◐ Refactor the auth middleware     ic · medium · phase 7/12 · 3 agents   ↓ ~9.4k tok · 2m
   ├─ claude/opus    ◐ editing…      4.1k tok · 41s
   ├─ codex/gpt-5    ◐ reviewing…    3.0k tok · 38s
   └─ gemini/pro     ◐ thinking…     2.3k tok · 12s
```

A **mini phase bar** can replace the bare `phase 7/12` when width allows (truthful: it has a
real denominator, unlike tokens):
```
◐ Refactor the auth middleware   ic · phase 7/12 [██████▌░░░░░] · 3 agents   ↓ ~9.4k tok
```

### Queued / done goals collapse to ONE line each
```
○ Add integration tests for /login   worker · queued                    waiting
✓ Update the API docs                worker · done · 12/12 · 1 agent     ↓ ~2.1k tok · 48s
```

### Top aggregate line (extends summarizeTurn)
```
▸ 3 goals · 2 running · 1 queued · 6 agents · 1.2m tok · 4m
```

### ASCII mockup — 3 goals running concurrently (tall terminal)
```
╭─ GOALS ──────────────────────────────────────────────────────────────────────╮
│ ◐ Refactor the auth middleware   ic · phase 7/12 · 3 agents     ↓ ~9.4k tok · 2m │
│    ├─ claude/opus   ◐ editing…     4.1k tok · 41s                                 │
│    ├─ codex/gpt-5   ◐ reviewing…   3.0k tok · 38s                                 │
│    └─ gemini/pro    ◐ thinking…    2.3k tok · 12s                                 │
│ ◐ Add integration tests for /login  worker · phase 1/5 · 2 agents  ↓ ~1.1k tok · 14s │
│    ├─ claude/opus   ◐ scaffolding…  0.7k tok · 14s                                │
│    └─ codex/gpt-5   ◐ thinking…     0.4k tok · 9s                                 │
│ ○ Update the API docs            worker · queued                    waiting       │
╰────────────────────────────────────────────────────────────────────────────────╯
▸ 3 goals · 2 running · 1 queued · 5 agents · 16.7k tok · 2m
⠹ Orchestrating 2 goals · 5 agents   esc to interrupt
```
This is the "wow" view: goal 1 deep in phase 7/12 with 3 agents, goal 2 just started phase
1/5, goal 3 queued — exactly the owner's "spoon-fed" picture.

### ASCII mockup — 12 goals (mostly queued/collapsed, viewport cap)
Collapse rules (see §4 `planGoalsPanel`): show RUNNING goals expanded up to a card budget,
collapse queued/done to one line each, and roll the overflow into a `+N more` line.
```
╭─ GOALS ──────────────────────────────────────────────────────────────────────╮
│ ◐ Refactor the auth middleware   ic · phase 7/12 · 3 agents     ↓ ~9.4k tok · 4m │
│    ├─ claude/opus   ◐ editing…    4.1k tok · 41s                                  │
│    └─ codex/gpt-5   ◐ reviewing…  3.0k tok · 38s                                  │
│ ◐ Migrate the session store      ic · phase 2/8 · 2 agents      ↓ ~3.1k tok · 1m │
│    └─ claude/opus   ◐ planning…   1.4k tok · 22s                                  │
│ ✓ Update the API docs            done · 12/12              ↓ ~2.1k tok            │
│ ✓ Bump deps                      done · 3/3                ↓ ~0.4k tok            │
│ ○ Add /login tests · ○ Wire CI · ○ Write changelog · +6 more queued              │
╰────────────────────────────────────────────────────────────────────────────────╯
▸ 12 goals · 2 running · 2 done · 8 queued · 5 agents · 31k tok · 4m
⠴ Orchestrating 2 goals · 5 agents   esc to interrupt
```
Note the queued goals coalesce onto a SINGLE row (`○ a · ○ b · ○ c · +6 more queued`) — they
carry no live detail, so one row is enough and it scales to any N.

### ASCII mockup — short terminal (rows ≈ 10)
The existing degradation kicks in: no room for cards → the compact one-liner (already built by
`compactGoalsSummary`, layout.ts:234), then status line.
```
╭─ GOALS ──────────────────────────────────────────────────────────────────────╮
│ 12 goals · 5 agents · 2 running · 2 done · 8 queued · ↓ 31k tok                  │
╰────────────────────────────────────────────────────────────────────────────────╯
▸ 12 goals · 2 running · 2 done · 8 queued · 5 agents · 31k tok · 4m
⠼ Orchestrating 2 goals · 5 agents   esc to interrupt
```

### Collapse / prioritization rules (the order)
1. **PlanPanel** (if a proposal is live) is highest priority — it gets its rows first
   (a turn is either proposing OR executing, so in practice they don't both show).
2. **Running goals, expanded** (header + agent rows), newest-active first, up to a budget.
3. **Running goals that don't fit → collapse to a 1-line header** (drop agent rows first).
4. **Done/failed goals → 1 line each**, then coalesced into a `✓ N done` summary line under
   pressure.
5. **Queued goals → always coalesced** to ONE `○ a · ○ b · +N more queued` row.
6. Still over budget → fall to the existing **compact** one-liner, then **hidden**.

The invariant is unchanged: the new `planGoalsPanel(goals, budget)` returns a row-counted
plan and `layoutForHeight` still proves `plannedRows + inputRows <= rows`.

## 4. PRECISE STATE / REDUCER / CORE-EVENT / LAYOUT / VIEW CHANGES

### state.ts (additive, all optional → no test churn for single-goal turns)
- `GoalView` gains `readonly phase?: { readonly current: number; readonly total: number }`
  (state.ts:64). Optional → absent renders no phase badge (never fabricated, matches the
  `risk?` honesty pattern at state.ts:86).
- New proposal slice:
  ```ts
  export interface PlanProposalGoal { readonly label: string; readonly tier: Tier; readonly risk?: Risk; }
  export interface PlanProposal {
    readonly goals: readonly PlanProposalGoal[];
    readonly summary?: string;            // "~3 agents · est. medium effort"
    readonly state: 'proposing' | 'editing';
  }
  ```
  `UiState` gains `readonly proposal: PlanProposal | null` (state.ts:143); `initialState`
  seeds `proposal: null` (state.ts:170). `turn/start` clears it (it's per-turn slice,
  reduce.ts:126).
- `AgentRunState` needs no change — `queued` already exists (state.ts:52).

### state.ts Action union (additive)
```ts
| { readonly type: 'plan/propose'; readonly proposal: PlanProposal }
| { readonly type: 'plan/edit' }                 // flip proposal.state → 'editing'
| { readonly type: 'plan/accept' }               // clear proposal (+ caller commits recap)
| { readonly type: 'plan/decline' }              // clear proposal
| { readonly type: 'goal/phase'; readonly goalId: string; readonly current: number; readonly total: number }
| { readonly type: 'goal/enqueue'; readonly goalId: string; readonly label: string; readonly tier: Tier; readonly risk?: Risk }
```
And `tier-start` gains `readonly goalId?: string` (state.ts:222) so a tier attaches to a
PRE-ENQUEUED goal instead of always appending a new one.

### reduce.ts changes
- `plan/propose|edit|accept|decline` → set/clear `state.proposal` (4 trivial cases). Accept
  does NOT commit — the impure caller commits the recap via `commit/raw` (keeps reduce pure
  of policy).
- `goal/enqueue` → append a `GoalView { state: 'queued', phase: {current:0,total}, agents: [] }`.
- `tier-start` (reduce.ts:198) — when `action.goalId` matches an existing queued goal, flip
  THAT goal to `running` and push the agent, instead of appending a new goal (reduce.ts:223).
  Multiple goals may now be `running` at once — this is the one behavioral relaxation.
- `goal/phase` → set `goals[goalId].phase = {current,total}` (immutable map).
- `settleActiveGoal` (reduce.ts:62) — today flips the LAST running goal. With concurrency it
  must settle the goal that matches the tier's `goalId` (add a `goalId` param to
  `flush-tier`, threaded from core-event.ts). `settleAllRunningGoals` (reduce.ts:98) already
  handles "settle every running at final" — keep as the safety net.

### core-event.ts changes
- `tier-start` map (core-event.ts:64) passes through `goalId` (needs a `goalId` on the
  `tier-start` CoreEvent in types.ts:649 — additive, optional).
- New CoreEvents (types.ts, all optional/additive): `goal-enqueue` (engine declares the goal
  set up front → `goal/enqueue` actions) and `goal-phase {goalId,current,total}` →
  `goal/phase`. The plan proposal can ride on the existing `intent`/`engagement` events
  (types.ts:606/615) which already carry a goal/plan frame, OR a new `plan` CoreEvent.
- `tier-done` (core-event.ts:96) passes through `goalId` so `flush-tier` settles the right goal.

### layout.ts changes (the cap-preserving collapse)
- `goalCardRows` (layout.ts:167) unchanged. Add `goalHeaderRow = 1` helper for collapsed goals.
- New `PLAN_PANEL_ROWS(proposal)` = 2 borders + 1 intro + N goal lines + 1 summary + 1
  question row; budgeted FIRST in `layoutForHeight` when `state.proposal !== null`.
- New `planGoalsPanel(goals, budget)` implementing §3's 6-step collapse, returning a
  discriminated plan:
  ```ts
  type GoalsMode =
    | { kind:'full'; rows: GoalRow[] }     // GoalRow = {goal, expanded:boolean} | {kind:'queued-coalesced', goals} | {kind:'done-coalesced', count}
    | { kind:'compact'; summary:string }   // existing
    | { kind:'hidden' }                    // existing
  ```
  The planner sums rows exactly as today and still asserts
  `plannedRows + inputRows <= rows` (layout.ts:290 contract unchanged).
- `summarizeTurn` (layout.ts:215) extends to surface running/queued/done counts when >1 goal
  is non-terminal (it already computes phases vs goals; just add the state breakdown like
  `compactGoalsSummary` does at layout.ts:242-254).
- Phase badge text: extend `goalBadge` (StatusBlock.tsx:190) to append `· phase X/Y` when
  `goal.phase` is set with `total > 0` (never when absent).

### StatusBlock.tsx changes
- New `PlanPanel` component (sibling of `Panels`) rendering the proposal slice + the
  `[y]/[e]/[n]` affordance row. Rendered above `Panels` in `StatusBlock` (StatusBlock.tsx:419)
  only when `state.proposal !== null`.
- `Panels` (StatusBlock.tsx:247) `full` branch handles the new `GoalRow` union: expanded goal
  → `GoalCard`; collapsed running/done → a 1-line header (new `GoalHeaderLine`); queued-
  coalesced → one `○ a · ○ b · +N more queued` line.
- `GoalCard` (StatusBlock.tsx:201) header gains the phase badge via the extended `goalBadge`.
- `StatusLine` (StatusBlock.tsx:290) verb when >1 goal runs: `Orchestrating N goals · M agents`
  (derive from `goals.filter(running)` + `totalAgentCount`, both already pure).

### App.tsx / menu loop (impure glue)
- Reuse `bridge.readKey()` (App.tsx:201) + `<KeyCapture>` (App.tsx:571) unchanged for the
  y/e/n confirm. Add `confirmPlanViaKey(out, readKey)` + `interpretPlanKey` (next to
  `interpretYesNoKey`).
- Edit path reuses `runQuestionSelector` (menu-question-flow.ts:38) for the change-picker and
  the existing InputBox for free-text edits — no new input primitive.
- `<Static>` stays append-only: the proposal lives ONLY in the live `proposal` slice; only the
  accepted/declined RECAP commits (one `commit/raw`).

### Invariants preserved
- **Cap**: every new row goes through `layoutForHeight`'s budget; the `plannedRows + inputRows
  <= rows` assertion is unchanged.
- **`<Static>` append-only**: proposals never enter `committed[]`; only a one-line recap does.
- **Honesty**: phase shown only with a real denominator; agent counts derived from real
  `AgentView`s (totalAgentCount, layout.ts:184); tokens stay text (no fake %).
- **Purity**: reduce/layout/core-event stay pure; readKey/confirm/edit stay in the impure glue.

## PHASING

**Phase A (ship first) — Confirm UI + 2-3 concurrent goals**
- state.ts: `proposal` slice + `GoalView.phase?` + the 6 new actions + `tier-start.goalId`.
- reduce.ts: plan/* cases; `goal/enqueue`; `tier-start` attach-to-queued; `goal/phase`;
  `settleActiveGoal`/`flush-tier` by goalId.
- core-event.ts + types.ts: `goalId` passthrough; `goal-enqueue`/`goal-phase` (or reuse
  intent/engagement for the plan).
- StatusBlock.tsx: `PlanPanel`; phase badge; `Orchestrating N goals` verb.
- layout.ts: `PLAN_PANEL_ROWS`; expand running goals + simple "queued/done → 1 line each"
  (no coalescing yet, fine for ≤3).
- glue: `confirmPlanViaKey`/`interpretPlanKey`; edit via `runQuestionSelector` + InputBox.

**Phase B (later) — 12-goal collapse**
- layout.ts `planGoalsPanel`: the full 6-step collapse + `+N more` coalescing + done/queued
  roll-ups.
- StatusBlock.tsx: `GoalHeaderLine` + coalesced-queued row rendering.
- `summarizeTurn` running/queued/done breakdown when >1 goal.

Phase A is the owner's core vision (the partner asks before doing; a couple of goals run
concurrently with phase X/Y). Phase B is pure presentation scaling — no new state, just a
richer `GoalsMode` plan, so it can land independently without touching reduce/core-event.
