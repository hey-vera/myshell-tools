# Multi-Goal Concurrent Execution Engine — Vision Design

Read-only architecture research. myshell-tools orchestrates claude/codex/opencode
provider CLIs via the user's OAuth subscriptions (no API keys). The owner wants to
decompose a confirmed plan into a SERIES of goals (~20) that orchestrate CONCURRENTLY,
watching "goal 1 phase 10 almost done, goal 2 phase 1 with N agents", honestly bounded
by a single subscription.

VERDICT UP FRONT: ~70% of the rendering machinery for this vision ALREADY EXISTS and is
unused on the multi-goal axis. The real new build is a bounded SCHEDULER that merges N
`orchestrate()` generators into one tagged CoreEvent stream. 20 goals flat-out is NOT
realistic on one subscription; the honest version runs 2–4 concurrently with the rest
queued.

---

## 1. How execution works TODAY (current-execution map)

### orchestrate() — the per-goal engine (`src/core/orchestrate.ts`)
- `orchestrate(task, deps, signal)` is an `async function*` yielding `CoreEvent`s
  (orchestrate.ts:247). One call = one user turn = one goal's worth of work.
- It is the tier-escalation loop: classify → route → run IC → optional cross-vendor
  review → assess → escalate/retry/accept → final. Main loop at orchestrate.ts:860
  (`mainLoop: while (attempts < deps.policy.maxAttempts)`).
- Each attempt routes a provider (route.ts), streams it via `streamProvider`
  (orchestrate.ts:139) which yields `{type:'provider-event', tier, event}` per event
  and accumulates text/usage/cost. Cancellation checked before and after each event
  (orchestrate.ts:152, 177).
- Cross-vendor failover within a tier: `triedByTier` Map + `failoverPool`
  (orchestrate.ts:777, 783). Escalation: `nextTierUp` / `admitManager` gate
  (orchestrate.ts:814, 834).
- Emits: `classified`, `tier-start` (carries `title` + `risk`), `provider-event`,
  `tier-done`, `escalate`, `failover`, `notice`, `final`. Exactly one `final`.
- It already has CONCURRENT siblings it can delegate the WHOLE turn to:
  - PANEL: `planPanel`/`runPanel` (orchestrate.ts:679, 688) — default OFF.
  - HEDGE: `planHedge`/`runHedged` (orchestrate.ts:718, 725) — default OFF.

### goal.ts — pure goal decision core (`src/core/goal.ts`)
- PURE only: `buildGoalTask` (per-turn instruction), `parseGoalSignal` /
  `parseTrailingGoalMarker` (GOAL_COMPLETE / GOAL_CONTINUE markers), `decideGoalNext`
  (continue/stop, goal.ts:296), `formatGoalProgress` (goal.ts:111 — already accepts
  `parallelModels` and renders "N models in parallel"), `capGoalLabel`.
- The loop itself is NOT here; it's in the interface layer (by design, goal.ts:7-8).

### The /goal runner (`src/interface/menu.ts` ~1829) — CONFIRMED SEQUENTIAL
- `runGoalLoop(goalText)` is a single `for (let i = 0; i < ceilings.maxIterations; i++)`
  (menu.ts:1850). ONE goal, ONE turn at a time.
- Each iteration: reload history → buildDeps → `buildGoalTask` → ONE
  `runTaskWithInputHooks(...)` (menu.ts:1894) under ONE `goalAc = new AbortController()`
  (menu.ts:1892) → parse marker → `decideGoalNext` → continue or stop.
- `maxIterations = DEFAULT_MAX_GOAL_ITERATIONS = 8` (goal.ts:56). No dollar ceiling on a
  subscription (menu.ts:1951). This is a SINGLE-goal autonomous loop, NOT multi-goal.

### Concurrency primitives that ALREADY EXIST
1. **`mergeCandidates` (ensemble.ts:573)** — THE reusable merge primitive. Runs N async
   generators concurrently and interleaves their yielded events via
   `Promise.race(pending.values())`, calling `onOutcome` the instant each returns
   (fastest-first). This is exactly the fan-in a multi-goal scheduler needs, one level up.
2. **`runPanel` (ensemble.ts:639)** — runs N providers concurrently for ONE turn +
   synthesizer. Emits `phase` events (`panel`/`synthesis`) + per-candidate tier-start/done.
3. **`runHedged` (hedge.ts:498)** — speculative race of 2 attempts via `Promise.race`
   (hedge.ts:610, 817), per-branch `AbortController` linked to caller signal
   (hedge.ts:556), cancel-the-loser. Demonstrates the cancellation pattern.
4. **Per-branch AbortController linking** (hedge.ts:556-563) — caller abort fans out to
   all branches; the model for ESC cancellation across N goals.
5. **cooldown.ts** — `availableAfterCooldown` de-prioritises a rate-limited provider for
   5 min (RATE_LIMIT_COOLDOWN_MS), NEVER strands (returns full list if all cooling).
6. **capability-budget.ts** — `pressureFromSignals` (0–3) + `decideShed` ordered shed
   plan. ADVISORY only (explicitly NOT a runtime governor — see file header lines 9-16).

### The UI is ALREADY MULTI-GOAL (the big find)
- `UiState.goals: readonly GoalView[]` (state.ts:144) — a LIST, not a single goal.
- `GoalView` (state.ts:64) has `id`, `label`, `state` (queued|running|done|failed),
  `tokens`, `agents: AgentView[]`, `tier`, `risk`. `AgentView` (state.ts:55) has
  provider/model/state/tokens/attempt.
- `StatusBlock` (StatusBlock.tsx) renders a `GoalCard` PER goal, each with per-agent
  tree rows, state glyphs (○ queued / ◐ running / ✓ done / ✗ failed), token meters.
- `summarizeTurn` (layout.ts:215) and `compactGoalsSummary` (layout.ts:234) already
  produce EXACTLY the owner's aggregate: counts running/queued/done/failed + agents +
  tokens → e.g. `2 phases · 4 agents · 1 running · 1 queued · ↓ 9.4k tok`.
- TODAY each `tier-start` appends one goal (reduce.ts:223-238). Within one sequential
  turn the tiers share a title, so `goalsAreSequentialPhases` (layout.ts:197) collapses
  them honestly to "N phases" of one request. There is NO multi-goal PRODUCER feeding
  this multi-goal renderer — that is the gap.
- The renderer consumes ONE `AsyncIterable<CoreEvent>` per turn: `for await (const ev of
  events)` (run-stream.ts:246); `runTask` calls `orchestrate(...)` once (run.ts:75).

## 2. The REAL concurrency ceiling on ONE subscription

### The hard facts
- Each `provider.run` spawns a CLI SUBPROCESS via execa (claude.ts:201,
  `execa(bin, args, {...})`; signal wired to execa termination at claude.ts:200). A
  "concurrent model call" = a live CLI child process holding an OAuth request in flight.
- There are ≤3 distinct provider CLIs: claude, codex, opencode. Each maps to ONE
  subscription's rate-limit bucket. Concurrent calls to the SAME provider share and
  contend for that ONE bucket.
- A single manager-tier turn can itself spawn 70+ tool calls (claude.ts:71) and run for
  minutes — so even ONE goal is heavy.

### The honest ceiling
- **Per-provider in-flight calls: ~1–2.** Stacking many concurrent calls on one
  subscription provider hits 429 fast; the system has no token-budget readout on
  subscription CLIs (capability-budget.ts:180-181 — "reactive-after-first-429 by
  design"). So the safe steady state is roughly ONE heavy call per provider at a time,
  maybe 2 for a brief overlap (which is exactly what hedge does, and only on hard turns).
- **System-wide concurrent goals: ~2–4.** With 3 providers signed in, 2–4 goals can run
  truly in parallel IF the scheduler spreads them across distinct providers. Beyond that
  you are double-booking a provider's bucket and inviting 429s + tail-latency.
- **Single provider signed in: ~1–2 goals.** Honest worst case — most goals queue.
- Latency, not dollars, is the felt cost: 20 goals × multi-tier serialised on 1–3
  buckets is a very long wall-clock run.

### What backpressure ALREADY does (reusable, but advisory)
- `pressureFromSignals` maps rate-limited-provider-count + recentQuotaError → 0..3.
- `decideShed` sheds OUR optional features in order under pressure (recap → memory width
  → intent pass), core answer never shed. But this sheds per-TURN overhead; it does NOT
  throttle goal concurrency. NEW work: a scheduler must read the same pressure signal and
  LOWER its active-goal cap (e.g. 4→2→1) when providers are throttled.
- `cooldown.availableAfterCooldown` already biases routing away from a throttled provider
  — the scheduler should reuse it to decide which goal can start on which provider.

CONCLUSION: design for an `activeLimit` of 2–4 (derived from signed-in provider count and
current pressure), everything else QUEUED. "20 goals running at once" is aspirational;
"20 goals, 2–4 active, rest queued, honest progress on all 20" is real.

## 3. DESIGN — the multi-goal concurrent execution engine

### Reusable vs new
REUSABLE (no change): `orchestrate()` (one call per goal-phase), `mergeCandidates`
fan-in pattern, hedge's linked-AbortController cancellation, cooldown,
`pressureFromSignals`/`decideShed`, the ENTIRE multi-goal UI (`GoalView[]`, `StatusBlock`,
`summarizeTurn`, `compactGoalsSummary`), `formatGoalProgress(parallelModels)`,
`decideGoalNext`, `capGoalLabel`.

NEW: (a) a decomposition step (confirmed plan → N goal specs), (b) a bounded SCHEDULER
module, (c) goal-tagging on CoreEvents so the merged stream maps each event to its goal
card, (d) a small reducer extension to key goals by a stable scheduler-assigned id rather
than `tier#attempt`.

### Where the scheduler lives — NEW module `src/core/scheduler.ts` (PURE core + executor)
Mirror the ensemble.ts/hedge.ts split exactly (the codebase's established pattern):
- PURE planning: `planSchedule(goals, opts)` → decides `activeLimit`, initial
  queued/running partition. Pure, unit-testable, no I/O. Honors `activeLimit =
  f(signedInProviderCount, pressure, policy)`.
- IMPURE executor: `runSchedule(goalSpecs, deps, signal)` — an `async function*` yielding
  goal-tagged CoreEvents, doing I/O ONLY through injected deps (same purity contract as
  runPanel/runHedged — that is allowed).

### How it interleaves with orchestrate() — ONE orchestrate per goal-phase
- Each GOAL is a sequence of phases. Each PHASE is exactly one `orchestrate()` (or one
  `runGoalLoop`-style autonomous turn) call — orchestrate stays the per-phase engine,
  untouched.
- `runSchedule` maintains a worker pool of size `activeLimit`. For each active goal it
  holds a live `orchestrate(...)` generator. It uses the SAME merge mechanic as
  `mergeCandidates` (ensemble.ts:573), one level up:
  - `Promise.race` over each active goal-generator's `.next()`;
  - each yielded `CoreEvent` is re-emitted WRAPPED with its goalId (see below);
  - when a generator returns (a phase's `final`), the scheduler advances THAT goal to its
    next phase (start a new `orchestrate()` for the next phase) or marks the goal done;
  - it then pulls the next QUEUED goal into the freed pool slot and starts its first
    phase. This is the bounded worker-pool: at most `activeLimit` generators live at once.
- Per-goal phase sequencing reuses `decideGoalNext` semantics (goal.ts:296): a goal's
  GOAL_CONTINUE marker → next phase; GOAL_COMPLETE → goal done.

### Goal tagging on CoreEvents (the one type seam)
The renderer keys goal cards off `tier-start`. To stack 20 distinct goals (not collapse
them as phases) the scheduler must attach a stable goalId. Two honest options:
- (Preferred, minimal) Add an OPTIONAL `goalId?: string` to the relevant CoreEvent
  variants (`tier-start`, `tier-done`, `provider-event`, `final`) in types.ts. orchestrate
  doesn't set it; the scheduler stamps it as it re-emits each goal's events. The reducer
  (reduce.ts) keys `GoalView.id` off `goalId` when present, falling back to today's
  `tier#attempt`. Additive + fail-soft → zero behaviour change on the single-turn path.
- The scheduler also sets the goal `label` (already supported via `tier-start.title`,
  types.ts:663) to each goal's human title, so cards read distinctly and
  `goalsAreSequentialPhases` (layout.ts:197) correctly reports "N goals" not "N phases".

### Progress events + honest aggregate
- Per-goal phase X/Y: the scheduler knows each goal's phase index + planned phase count;
  surface as the goal `label`/badge or a notice. `formatGoalProgress` already renders
  "steps done/total" from a work-contract roadmap (goal.ts:159) — reuse the roadmap as
  the per-goal phase list.
- Per-goal agents + queued/running/done: ALREADY rendered by StatusBlock from GoalView
  state. The scheduler just emits the right tier-start/tier-done (running/done) and seeds
  QUEUED goals as goal cards in `queued` state (needs a tiny reducer addition: a
  `goal/queued` action, or stamp a tier-start-less placeholder goal).
- Aggregate "3 goals · 2 running · 1 queued · 28 agents": `compactGoalsSummary`
  (layout.ts:234) produces this verbatim TODAY from `goals[]`. Nothing new needed once
  queued goals are represented in state.

### Cancellation (ESC) — fan-out
- The scheduler owns one parent `AbortController` per run; each active goal-phase gets a
  child controller linked to the parent (exactly hedge.ts:556-563). ESC aborts the
  parent → all active orchestrate generators see `signal.aborted` and stop cleanly
  (orchestrate's streamProvider checks abort each event, orchestrate.ts:177). Queued goals
  simply never start. One `final`-style summary emitted on cancel.

### Degrade under rate-limit pressure (queue, don't hammer)
- Before pulling a queued goal into a free slot, the scheduler computes
  `pressureFromSignals({rateLimitedProviderCount, recentQuotaError})`
  (capability-budget.ts:183) from the SAME signals run-stream tracks (rateLimitedProviders
  set). It lowers `activeLimit` (e.g. pressure 1→cap 2, 2→cap 1, 3→hold/queue all) and
  uses `availableAfterCooldown` (cooldown.ts:49) to pick a goal whose preferred provider
  is NOT cooling down. On a 429 the goal's phase fails-soft → requeue with backoff rather
  than retry-hammer. This makes "queue, don't hammer" real instead of a claim.

## 4. HARD CONSTRAINTS — how the design satisfies them
- **Subscription-OAuth only, no metered API, no new heavy deps.** Scheduler is pure TS +
  the existing execa-spawned provider CLIs. The merge primitive is `Promise.race` (already
  used in ensemble/hedge). No vector DB, no embeddings, no new package.
- **Degrade under rate-limit pressure.** `pressureFromSignals` + `availableAfterCooldown`
  drive `activeLimit` down and bias provider selection; 429 → requeue-with-backoff, never
  hammer. (Section 3.)
- **Cancelable (ESC).** Parent/child AbortController fan-out (hedge pattern). (Section 3.)
- **Emits events the existing reducer/StatusBlock can render.** The whole point: it emits
  the SAME CoreEvents, optionally goal-tagged. The reducer + StatusBlock + summaries are
  already multi-goal. Only additions: optional `goalId` field + a `goal/queued` reducer
  action. Both additive/fail-soft.
- **20 goals flat-out is NOT realistic.** Design ships `activeLimit` 2–4 with the rest
  queued; the user watches all 20 cards (running + queued + done) with honest aggregate.

## 5. Token/cost honesty (20 goals × multi-tier is expensive)
- No dollar bill on a subscription, but quota + wall-clock are real. The design must
  surface this BEFORE committing, mirroring runPanel's up-front honest notice
  (ensemble.ts:678 — "N quota-consuming runs, may take longer").
- Decomposition step should emit an ESTIMATE up front: `~N goals × ~M phases ≈ K
  quota-consuming model runs; ~2–4 run at a time; rough wall-clock estimate`. K is a
  count of runs (honest), NOT a fabricated dollar figure (matches the tokens-not-dollars
  contract; see types.ts:683 — cost "NOT shown on the hot path").
- OPT-IN gate: present the plan + the K-runs estimate + activeLimit and require explicit
  confirmation before the scheduler starts (reuse the existing structured-question /
  confirm flow used for plans). No autonomous 20-goal spend without a yes.
- Honor a turn/run CEILING like `decideGoalNext`'s `maxIterations` (goal.ts:324), but at
  the SCHEDULE level: a total-runs ceiling that stops + reports honestly when hit, rather
  than burning quota silently.

## PHASED PLAN (early phase is a bounded, shippable step toward the vision)

### Phase 0 — Tagging seam (tiny, enabling, zero behaviour change)
- Add optional `goalId?: string` to `tier-start`/`tier-done`/`provider-event`/`final` in
  types.ts. Add a `goal/queued` reducer action + key `GoalView.id` off `goalId` when
  present. orchestrate untouched (never sets it). Single-turn path byte-for-byte
  unchanged. SHIP-ABLE alone; unlocks everything else.

### Phase 1 — Bounded scheduler MVP behind a flag (the shippable vision slice)
- NEW `src/core/scheduler.ts`: PURE `planSchedule` + executor `runSchedule` that runs a
  STATIC list of independent goals (no auto-decomposition yet — user supplies N goals, or
  a trivial splitter) with `activeLimit = min(2, signedInProviders)`, merging via the
  `mergeCandidates` pattern, stamping goalId + label per goal, seeding queued goals as
  cards. ESC fan-out cancellation. Reuse `cooldown` for provider spread. Behind a default-
  OFF flag (mirrors panel/hedge rollout). This ALONE delivers "watch goal 1 + goal 2 with
  queued rest" — the owner's core ask — with honest 2-active bounding.

### Phase 2 — Pressure-aware queueing + per-goal phases
- Wire `pressureFromSignals` to vary `activeLimit` (2..4 / down to 1) and 429→requeue-
  with-backoff. Add per-goal multi-PHASE sequencing (each phase = one orchestrate; reuse
  `decideGoalNext` + work-contract roadmap for phase X/Y). Now goals show real
  phase progress ("goal 1 phase 10/10, goal 2 phase 1/8").

### Phase 3 — Decomposition + cost opt-in
- A decompose step (model-assisted or rules) turns a CONFIRMED plan into goal specs with
  per-goal phase roadmaps; emit the up-front K-runs estimate + activeLimit; require
  explicit confirmation (existing confirm/question flow); enforce a total-runs ceiling.
  This closes the "maybe 20 goals" loop honestly.

### Phase 4 — Polish
- Raise default `activeLimit` to 3–4 when ≥3 providers signed in + Max mode; tune the
  summary/compact layout for many stacked cards; consider per-goal native-session resume.

## Real vs aspirational (flagged)
- REAL TODAY: single-goal sequential /goal loop; multi-goal UI rendering + aggregate
  summaries; concurrent panel/hedge for ONE turn; cooldown + advisory pressure shedding;
  the merge-generators primitive.
- ASPIRATIONAL / NEW: the scheduler that fans out N goals; goal-tagging on events; queued-
  goal cards; pressure-driven activeLimit; plan decomposition + cost opt-in.
- HONESTY FLAG: "20 goals running concurrently" is not achievable on one subscription;
  the truthful product is 2–4 active + the rest queued, with all 20 visible and
  progressing. The codebase's own capability-budget header already states there is no
  token-budget readout on subscription CLIs — concurrency control must be reactive
  (post-429) + conservative, which is why the activeLimit stays low.
