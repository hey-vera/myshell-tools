## 1. What \"true 10/10\" means for THIS product

Not adjectives. Observable behaviors a user would feel:

| # | Acceptance criterion | Why it matters |
|---|---|---|
| AC1 | **One chat, one voice.** The user types in natural language. Every turn — regardless of whether it's a question, a bug report, or a 20-page build — routes to the right model/effort/decomposition with zero user knob-turning. The user never thinks about models, tiers, or effort. | Core promise of the product. |
| AC2 | **Byproduct intent — zero added latency.** Intent classification costs exactly $0 and 0 ms of added wall-clock. The user's turn already paid for the inference; the routing hints fall out as structured side-output of that same call. No separate router model ever fires. | `auto-mode-design.md` §2 conclusion — predict-and-commit is the architecture. |
| AC3 | **Context never bloats.** After 100 turns and 5 concurrent goals, the per-turn context stays bounded (~the size of 1 curated goal-lane + essential orientation). The user can switch between goals and not feel the system getting stupider. | This is the "manager-as-curated-state" principle. |
| AC4 | **Every build-intent turn produces a visible, inactive plan skeleton** (goals → sub-goals) that the user can review before a single line of code is written. The skeleton decomposes just-in-time — to-dos materialize only as work reaches each sub-goal. | Phase 1 contract. Prevents "one giant call that times out." |
| AC5 | **Auto mode predicts the right rung upfront and escalates only on objective failure** — never on model self-confidence. A failed test/typecheck/lint, a scope explosion, or explicit pushback are the ONLY triggers. The user can audit WHY via a one-line receipt per turn. | `auto-mode-design.md` §2.3 — research-mandated. |
| AC6 | **Ghost text is goal-aware and local-first.** Tab on empty prompt suggests the next action given board state (approve/skip/next-todo). While-typing completion is debounced, uses history+trie+paths for zero-model-call resolution first, and fails silent (no error visible to user). Volume stays tiny. | Problem #3 from user complaints. |
| AC7 | **Windows is a first-class platform.** The test suite passes on Windows with ≤5 known-env failures (all pre-existing, documented). No 0o600-permissions bugs, no symlink crashes, no path-separator issues. | User runs on Windows. `HANDOFF.md` notes 35–92 env failures. |
| AC8 | **Goals never get stuck.** Every goal's lifecycle state is reconciled against reality. Timeouts are preempted by decomposition into small units. On unrecoverable failure, the user gets an honest "here's exactly what happened" — no silent hanging. | Phase 3 contract. |
| AC9 | **The UX surfaces are polished and skimmable.** The menu goal section is one neat line, not a chunky block. The goal board is hierarchical, glancable for vibe-coders, expandable for pros. | Problems #1 and #5. |
| AC10 | **Quota is visible and attributable.** Per-turn and per-goal spend is surfaced. Mode dial wired to visible spend. The user trusts the system isn't wasteful. | Phase 6 contract. |

- **Goal:** When the manager cycle activates a goal, call `decompose()` to materialize the NEXT sub-goal's to-dos just-in-time, using the skeleton's sub-goal as input. To-dos are NOT generated for the whole goal upfront — only for the sub-goal about to be worked on.

## 6. Open questions for the user

1. **Were PRs #5–#12 actually merged?** The HANDOFF.md claims they were, but the features they describe (MYSHELL_AUTO_BRAIN, MYSHELL_LEVEL_DIAL, MYSHELL_DRAFT_GOALS, RungTuple, fuseRung, draftGoalSkeleton) don't exist in the codebase. Were these PRs reverted, or was the HANDOFF written aspirational-style, or did the implementation take a completely different path (building Governor/Flagship instead)?

2. **Is the Governor the right architecture for Auto mode?** The design docs describe a simpler Layer A/B model (predict-and-commit + escalate-on-evidence). The actual code has an 886-line Governor with detailed lever budgets, turn-shape classification, and multi-dimensional allocation. The simpler design might be better — or the Governor might be right and the docs are just wrong. Which direction should workers build toward?

3. **Should the "one chat" vision be the interactive menu only, or also `myshell-tools run`?** The HANDOFF implies both.
