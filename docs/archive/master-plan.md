# myshell-tools Master Plan

myshell-tools has the right product ambition but the current TUI is still an imperative, append-only command transcript wearing an Ink UI. Recent patches reduced one visible symptom on the home screen, but they did not establish a single navigation model, a single input owner, or bounded rendering for the rest of the menu tree. The result is predictable: submenu keys can be consumed by a hidden editor, React work grows with every navigation, authentication inherits provider-CLI behavior instead of owning its return destination, and “default shell” is stored as intent rather than proven startup behavior. These are architectural defects, not polish bugs.

## Round 1: Three Concrete Defects

### 1. Menu lag / sluggish controls / multiple presses

#### Root Cause

The production UI defaults to Ink (`src/interface/ui/flag.ts:1-34`), but menu behavior is still driven by imperative `out.write()` plus one-shot `readMenuKey()` calls. The complete path is:

1. `startMenu()` resolves a raw TTY and mounts Ink (`src/interface/menu.ts:6510-6523`). Ink receives that stream at `render()` (`src/interface/ui/mount.tsx:647-665`).
2. One continuously mounted `InputBox` owns `useInput` (`src/interface/ui/InputBox.tsx:656-659`). It sends a key to menu capture only while `readPending()` is true; otherwise the same key edits the hidden input buffer (`src/interface/ui/InputBox.tsx:433-439`, `src/interface/ui/InputBox.tsx:631-651`).
3. The home loop arms its special capture flag before painting (`src/interface/menu.ts:6974-6985`), paints the entire home frame (`src/interface/menu.ts:6938-6955`), then finally awaits one key (`src/interface/menu.ts:7029-7050`). `InkAppBridge.readKey()` either drains its FIFO or installs one resolver (`src/interface/ui/App.tsx:266-279`); `InputBox` normalizes and resolves it (`src/interface/ui/App.tsx:743-752`); `readMenuKey()` classifies it (`src/interface/menu-key-confirm.ts:205-222`).
4. On every printable home action, the code promotes the roughly full-screen frame into the permanent transcript and disables capture before entering the child flow (`src/interface/menu.ts:7065-7075`).
5. Child screens then print imperatively and arm their own one-shot reader only after printing. Representative examples are Settings (`src/interface/menu-settings.ts:384-428`), Manage Conversations (`src/interface/menu-conversations.ts:47-70`), and the account menus (`src/interface/menu-claude-accounts.ts:463-494`).

That pipeline contains four concrete defects:

- **The key-loss fix is scoped only to home.** The comments and wiring explicitly say capture is main-menu-only (`src/interface/menu.ts:6649-6654`) and explicitly disarm it before every sub-flow (`src/interface/menu.ts:7070-7075`). While a submenu is doing pre-paint I/O, `_keyResolver` is null and `_menuCaptureActive` is false, so `readPending()` is false (`src/interface/ui/App.tsx:743-750`). The composer is visually hidden outside chat but its input hook remains active (`src/interface/ui/App.tsx:727-743`). A fast key therefore goes into the invisible `InputBox` editor at `src/interface/ui/InputBox.tsx:631-651`, not into the submenu. The user must press again after the submenu reaches `readMenuKey()`. This exactly produces “one action takes multiple presses,” and can also leak invisible menu letters into a later chat composer.
- **The supposedly bounded home frame is permanently appended on every action.** `promoteFrame()` dispatches `chrome/promote` (`src/interface/ui/mount.tsx:196-200`), and the reducer copies the entire frame into `committed[]` (`src/interface/ui/reduce.ts:228-233`). This happens for every non-empty key before the action is even validated (`src/interface/menu.ts:7065-7075`). The fix stopped repeated no-op frames from accumulating, but normal navigation still adds a full home screen to the permanent `<Static>` transcript on every action.
- **Submenus bypass frames and dispatch once per printed line.** Outside `beginFrame()`/`endFrame()`, every newline becomes a `commit/raw` dispatch (`src/interface/ui/mount.tsx:166-175`). Each dispatch creates a new `committed` array (`src/interface/ui/reduce.ts:39-42`, `src/interface/ui/reduce.ts:202-207`) and synchronously pushes a React state update (`src/interface/ui/mount.tsx:96-104`). The committed component then remaps the full transcript whenever that array changes (`src/interface/ui/App.tsx:489-503`). Account edit screens alone issue more than a dozen writes per loop (`src/interface/menu-claude-accounts.ts:218-238`). This is progressive O(history × writes) reconciliation, not a stable full-screen TUI.
- **The legacy fallback also has a key-loss race and is chunk-based, not key-based.** Every read snapshots and removes all `data`/`keypress` listeners, toggles raw mode, then restores listeners (`src/interface/menu-readline.ts:351-398`). A `data` event is treated as exactly one key (`src/interface/menu-readline.ts:360-363`), while `readMenuKey()` discards any printable chunk whose length is not exactly one (`src/interface/menu-key-confirm.ts:225-244`). Two rapid letters coalesced into one buffer are both thrown away. Between one-shot readers, readline owns the stream again, recreating the same render-to-reader race.

There is no debounce or throttle on menu keys, and there is no full-screen clear per key. The latency is caused by lost keys, growing append-only render state, many state dispatches per screen, and blocking work on the navigation path. Blocking examples include a subscription read inside `paintMenu()` (`src/interface/menu.ts:6938-6948`), synchronous environment refresh on the legacy path (`src/interface/menu.ts:7021-7027`), two consecutive conversation-list reads on Manage entry (`src/interface/menu-conversations.ts:48-67`), and a subscription-file read before every account-menu paint (`src/interface/menu-claude-accounts.ts:463-471`).

#### Why it happens

Ink was added as an adapter under the old procedural menu rather than becoming the owner of menu state. The code therefore has two incompatible models: React expects state-driven, bounded replacement; the menu code expects terminal output to be a permanent log followed by a one-shot raw read. The home-only FIFO papers over the interval between those operations, but child screens retain the race. Promoting every home frame and committing every child line also defeats `<Static>`’s intended use: historical chat output belongs there; current menu chrome does not.

#### Fix Plan

1. **Make key capture route-scoped, not home-scoped.** Replace `setMenuCaptureActive(boolean)` with `setKeyScope({kind: 'menu', routeId})` and keep it armed for the complete lifetime of every menu/submenu; only switch it off for actual free-text fields and inherited provider children. Anchor the controller at `src/interface/menu.ts:6494-6654`, route it through the existing bridge at `src/interface/ui/App.tsx:217-284`, and make `InputBox` send menu-scoped keys to it before editor mutation at `src/interface/ui/InputBox.tsx:433-439`. Clear queued keys by route generation, not whenever a parent calls `false`, so stale keys cannot activate the next screen.
2. **Turn every menu into an ephemeral replaceable surface.** Generalize the existing frame API at `src/interface/ui/mount.tsx:154-200` to `replaceSurface(routeId, lines)` and render Settings, Library/Manage, account lists, account edit, mode, privacy, and setup through one dispatch. Convert the current write sites at `src/interface/menu-settings.ts:71-135`, `src/interface/menu-conversations.ts:47-70`, and `src/interface/menu-claude-accounts.ts:218-238` first; apply the same conversion to the Codex/Grok/OpenCode sibling files. Menu chrome must never enter `committed[]`.
3. **Delete unconditional home promotion.** At `src/interface/menu.ts:7065-7069`, clear/replace the active menu surface when navigating instead of calling `promoteFrame()`. Keep only explicit, short receipts (for example, “Account created”) as committed output. Update `chrome/promote` at `src/interface/ui/reduce.ts:228-233` either to disappear or to be reserved solely for a deliberately requested transcript snapshot.
4. **Batch output state changes.** Change the sink at `src/interface/ui/mount.tsx:166-175` so a logical screen/receipt commits one array action, not one action per newline. Add a reducer action accepting multiple raw lines beside `commit/raw` at `src/interface/ui/reduce.ts:202-207`. Do not call `bridge.pushState()` when `reduce()` returns referentially identical state; enforce that at `src/interface/ui/mount.tsx:101-104`.
5. **Use one persistent key decoder.** Replace the listener destruction in `src/interface/menu-readline.ts:351-403` with one lifecycle-owned keypress dispatcher created beside the single `LineReader` at `src/interface/menu.ts:6582-6621`. Decode all events in a chunk and enqueue them individually; do not discard `raw.length > 1` wholesale at `src/interface/menu-key-confirm.ts:232-239`. Ink and legacy should consume the same normalized `MenuInputEvent` contract.
6. **Remove I/O from key-to-next-frame latency.** Cache subscriptions and conversation metadata in the menu session. Start refreshes after the destination surface is visible, as the home already attempts for ledger/lists at `src/interface/menu.ts:6987-7015`. Eliminate the duplicate Manage read at `src/interface/menu-conversations.ts:48-67`; refresh account data after mutations rather than before every paint at `src/interface/menu-claude-accounts.ts:463-471`. Keep provider detection outside navigation unless an auth/install action dirtied it (`src/interface/menu.ts:6702-6726`).
7. **Add regression instrumentation and tests.** Extend the existing single-key suites around `test/ui/menu-submenu-single-key.test.tsx:1` and `test/ui/menu-capture-fifo.test.tsx:1` to inject a key during each submenu render and assert exactly one action with an empty editor afterward. Add a reducer/store test beside `test/ui/app.test.tsx:1` asserting 1,000 menu transitions do not increase `committed.length` and require at most one state dispatch per frame. Add a legacy stream test beside `test/unit/menu.test.ts:1` that emits `Buffer.from('mm')` and proves two separately queued key events rather than one discarded chunk.

#### Risk / Regression Notes

- Do not route printable input away from chat or genuine text prompts. The scope transition must be explicit and generation-tagged.
- Do not use `<Static>` for replaceable menu chrome; doing so reintroduces terminal scrollback duplication.
- A persistent key decoder must correctly preserve escape sequences, pasted text, Ctrl combinations, and inherited-child suspension. Reuse `normalizeInkKey()` semantics (`src/interface/ui/App.tsx:411-437`) as the shared contract rather than creating divergent mappings.
- The legacy pipe/test path must remain line-oriented; raw single-key decoding is only for an actual TTY (`src/interface/menu-readline.ts:298-329`).

#### Definition of Done

- A key injected at every point from “route selected” through “submenu reader armed” triggers exactly one action; zero keys land in the hidden composer.
- 1,000 home↔submenu transitions leave `UiState.committed.length` unchanged except for explicit receipts and keep the live menu surface bounded to one screen.
- Each menu frame causes at most one reducer dispatch and one React state push.
- A burst containing two menu keys is decoded as two ordered events; it is never silently discarded.
- Source-level timing instrumentation reports p95 key-to-visible-frame below 50 ms with cached data in the PTY smoke harness, and no synchronous filesystem/provider probe occurs in that interval.

### 2. Post-login misrouting into provider chat

#### Root Cause

The report is fully supported for Claude and only conditionally supported for the other providers. The source does **not** contain a universal “after login, open provider chat” branch. Instead:

- Claude login is literally a native Claude TUI session: both browser and code tables execute `claude /login` (`src/commands/login.ts:56-65`, `src/commands/login.ts:72-92`). The code explicitly tells the user to manually type `/exit` or press Ctrl+C/Esc after authentication (`src/commands/login.ts:82-92`). Therefore authentication completes while the foreground child remains Claude’s chat UI. myshell cannot restore Manage until that child exits because it awaits `child.done` before verification (`src/commands/login.ts:212-243`). This is the direct source-backed misrouting.
- Codex, OpenCode, and Grok use auth-specific commands (`codex login`, `opencode auth login`, `grok login --oauth`, and device variants) at `src/commands/login.ts:56-65` and `src/commands/login.ts:94-125`; by source contract those should exit after auth. If they remain in chat in a particular CLI version, the current generic child contract cannot detect or correct it because it also waits for exit before probing.
- Navigation after `runLogin()` is accidental lexical continuation, not explicit state. `runLogin()` returns only a numeric status (`src/commands/login.ts:303-327`, `src/commands/login.ts:341-434`) and knows nothing about its origin. The Accounts flow happens to stay inside a local `while` (`src/interface/menu.ts:7223-7315`), while the New/Continue auth gate returns `true` after login (`src/interface/menu.ts:502-574`) and its callers immediately enter `runChatLoop()` (`src/interface/menu.ts:7082-7097`, `src/interface/menu.ts:7105-7116`). There is no navigation stack or typed return destination, so “login from Manage” and “login because New needs auth” are indistinguishable to the login service itself.
- Terminal ownership is restored mechanically, not navigationally: the menu reader is suspended/resumed around the child (`src/commands/login.ts:228-241`, `src/commands/login.ts:377-387`), but no route snapshot is restored afterward.

The broad design flaw is real even where the current lexical call happens to return correctly: authentication owns a subprocess, callers own ad hoc loops, and nobody owns a return-to-origin contract.

#### Why it happens

The Claude `/login` workaround optimized paste reliability by launching an entire chat application. That made “sign in” and “open provider chat” the same subprocess. Separately, the menu has nested function calls rather than route state, so return behavior depends on which caller resumes after an `await`. This is fragile under account creation, re-auth, first-run onboarding, auth-gated chat, and future providers.

#### Fix Plan

1. **Make login return an outcome, never a destination.** Replace `Promise<number>` at `src/commands/login.ts:316-327` with a typed `LoginResult` containing provider, authenticated/cancelled/failed status, and verification detail. Keep standalone CLI exit-code translation at `src/cli.ts:499-510`; menu code should consume the typed result.
2. **Introduce an explicit route stack.** Add `src/interface/menu-navigation.ts:1 (new)` with `MenuRoute`, `NavigationSnapshot`, `push`, `pop`, `replace`, and `restore(snapshot)`. Instantiate it at `src/interface/menu.ts:6494`, and replace local `while`/return assumptions in Accounts (`src/interface/menu.ts:7180-7319`), Settings (`src/interface/menu.ts:7526-7529`), and Library (`src/interface/menu.ts:7148-7176`) with route transitions.
3. **Capture origin before authentication.** At every menu login call (`src/interface/menu.ts:7238-7249`, `src/interface/menu.ts:7277-7281`, `src/interface/menu.ts:7309-7313`, and the direct provider branches at `src/interface/menu.ts:7346-7498`), take a navigation snapshot and restore it in `finally` after terminal resume and environment refresh. Account create/re-auth calls at `src/interface/menu-claude-accounts.ts:96-126` and `src/interface/menu-claude-accounts.ts:298-323` must receive/pass that snapshot. Apply the same change to Codex and Grok account modules.
4. **Make chat continuation explicit only for chat-gated auth.** `promptForAuthBeforeChat()` at `src/interface/menu.ts:502-574` should return `{login, nextRoute: chatRoute}` only after verified success. New/Continue callers at `src/interface/menu.ts:7082-7138` may then `replace(chatRoute)`. An Accounts-origin login must always restore Accounts/Provider Account, regardless of success, cancel, or child exit code.
5. **Stop using a full chat TUI as the normal Claude auth command.** Change the Claude entries at `src/commands/login.ts:56-92` to the auth-only `claude auth login` path already named elsewhere in the codebase (`src/providers/errors.ts:167`) and documented by the repository (`README.md:56-68`). Preserve `/login` only as a clearly labelled compatibility fallback for CLI versions/auth methods that require the selector. If fallback is used, start credential polling concurrently with the child instead of waiting at `src/commands/login.ts:233-243`; once verification succeeds, terminate the fallback child, await cleanup, restore stdin, and restore the origin route. Bound polling and never kill on an unverified state.
6. **Correct stale documentation and tests.** `README.md:56-68` currently claims `claude auth login` while production executes `/login`; make docs and implementation agree. Extend `test/unit/login.test.ts:1` for auth-only command selection/result typing and add route-origin cases to `test/unit/menu-flow.test.ts:1`: Accounts→Claude login success/cancel/failure returns Accounts; account re-auth returns the exact edit screen; New→login success alone proceeds to chat.

#### Risk / Regression Notes

- The repository history says `/login` was chosen because bare `auth login` skipped Claude’s method selector. The fix must preserve alternate Console/Bedrock/Vertex paths as an explicit fallback, not silently remove them.
- Killing a provider TUI immediately after credential detection can leave terminal modes dirty. Always await child completion, restore through the existing suspend/resume seam, and repaint only after resume (`src/commands/login.ts:228-241`).
- A successful process exit is not proof of authentication; retain the real credential probe (`src/commands/login.ts:264-286`).
- Do not let standalone `myshell-tools login` acquire menu navigation dependencies. Route restoration belongs in the menu orchestration layer.

#### Definition of Done

- From every Accounts, provider-account-create, and provider-account-edit/re-auth route, successful/cancelled/failed login returns to the exact originating route with its selection context intact.
- No normal login flow leaves the user at a provider chat prompt after credentials verify.
- New/Continue auth gating is the only flow that enters myshell chat after login, and it does so via an explicit route assertion.
- Tests cover all four providers and all three outcomes (success/cancel/failure), plus Claude compatibility fallback.
- Terminal input has exactly one owner before, during, and after the child; the first key after return is accepted once.

### 3. Default-shell launch and Ctrl+C semantics

#### Root Cause

##### (a) Default-shell launch

Three source-level problems make “enabled” weaker than “fresh Replit shell launches myshell”:

- **The recursion guard leaks across shell processes.** The generated bash/zsh hook checks `$MYSHELL_LOADED`, exports it, and then launches (`src/commands/install.ts:124-136`). Because it is exported, any new interactive child shell inherits `MYSHELL_LOADED=1` and skips autolaunch. The variable is also set before confirming `myshell-tools` exists (`src/commands/install.ts:133-136`), so one PATH miss suppresses later nested-shell attempts. PowerShell has the same process-inherited global environment design (`src/commands/install.ts:149-158`).
- **Configuration says “on” before a physical hook is proven.** The default config is `setAsDefault: true` even when no rc file has been written (`src/infra/config.ts:633-646`), and missing/corrupt config returns that value (`src/infra/config.ts:673-700`). On Replit, intent persists in the workspace but `~/.bashrc` can be recreated. The only self-heal runs *inside an already-started myshell process* (`src/cli.ts:833-866`). It cannot bootstrap the first fresh shell after the hook disappears; the product must already have been manually launched for the repair code to execute. The installer itself acknowledges this dependency (`src/commands/install.ts:783-789`).
- **The Replit wrapper is ephemeral-home wiring.** It correctly replaces a Nix-store `.bashrc` symlink with a writable wrapper (`src/commands/install.ts:556-618`), but that wrapper still lives at `$HOME/.bashrc` (`src/commands/install.ts:566-568`). Replit recreation can restore the original symlink, removing the launch hook until the circular self-heal above runs.

There is also a state-consistency bug in the Settings toggle: it writes `defaultShellOptOut: !enable` even when install/uninstall fails and `setAsDefault` remains unchanged (`src/interface/menu-settings.ts:289-304`). A failed enable records no opt-out, so the next load migration can flip the setting back to true (`src/infra/config.ts:688-694`) without a working hook.

##### (b) Ctrl+C

Ctrl+C behavior is fragmented across four incompatible implementations:

- `readMenuKey()` converts Ctrl+C/Ctrl+D to `null` (`src/interface/menu-key-confirm.ts:208-218`, `src/interface/menu-key-confirm.ts:225-244`). At the home loop, `null` immediately breaks and exits (`src/interface/menu.ts:7052-7055`).
- Some child menus happen to treat `null` as Back because their local function returns, e.g. account edit (`src/interface/menu-claude-accounts.ts:238-240`) and account list (`src/interface/menu-claude-accounts.ts:493-496`). This is accidental call-stack behavior, not a global rule.
- Confirm prompts re-raise SIGINT to the process (`src/interface/menu-key-confirm.ts:159-167`, `src/interface/menu-key-confirm.ts:301-316`), bypassing menu back semantics entirely.
- Chat uses one press for cancel/hint, two for menu, and three for shell (`src/interface/menu-display.ts:386-410`, `src/interface/menu.ts:1599-1641`), while a raw provider session uses two for menu (`src/interface/menu-raw-session.ts:15-29`, `src/interface/menu-raw-session.ts:111-137`). There is no app-level two-press controller.

#### Why it happens

`MYSHELL_LOADED` is being used as both a recursion guard and a lifetime/session guard; those are different scopes. Exporting it makes the guard outlive the shell invocation that set it. The persisted config similarly conflates desired state with verified installation state. Ctrl+C is fragmented because navigation is represented by nested awaits/returns, so each prompt interprets a null or signal locally instead of dispatching one navigation event.

#### Fix Plan

1. **Make the shell guard shell-instance-specific.** At `src/commands/install.ts:124-176`, replace boolean `MYSHELL_LOADED` with a PID/runspace token. For bash/zsh, launch only when `${MYSHELL_LOADED_SHELL_PID:-}` differs from `$$`, then export the current `$$`; a child interactive shell has a different PID and can launch, while re-sourcing the same rc cannot recurse. Set the token only after `command -v myshell-tools` succeeds. Use `$PID` equivalently for PowerShell. Keep `MYSHELL_SKIP` as the explicit inherited opt-out.
2. **Separate desired, installed, and verified state.** Keep `setAsDefault` as user intent but derive the UI’s “on” receipt from `isHookInstalled()` (`src/commands/install.ts:464-492`). At `src/interface/menu-settings.ts:289-304`, update both config fields only on successful install/uninstall; on failure preserve both previous values. Do not let the migration at `src/infra/config.ts:688-694` claim enabled installation.
3. **Remove the Replit cold-start circularity with a managed `onBoot` bootstrap.** During a successful Replit install at `src/commands/install.ts:659-689`, write a non-interactive, idempotent heal script to the persistent workspace (for example `.myshell-tools/replit-shell-bootstrap.sh`). Add a narrowly scoped, line-preserving `.replit` updater beside `ensureReplitShellHook()` at `src/commands/install.ts:556-640`: parse the single existing TOML `onBoot` string, append `; command -v myshell-tools >/dev/null 2>&1 && MYSHELL_SKIP=1 myshell-tools replit-heal >/dev/null 2>&1 || true` once, and remove only that exact suffix on uninstall. This repository already has a real `onBoot` command that must be preserved byte-for-byte (`.replit:33-34`); never add a second `onBoot` key. Add a non-UI `replit-heal` command at the command dispatch beside install/uninstall (`src/cli.ts:628-632`) that calls `ensureReplitShellHook()` and exits. Keep the existing launch-time repair (`src/cli.ts:846-866`) only as fallback. If `.replit` cannot be parsed or safely updated, fail installation honestly and leave the setting unverified; a code path that only runs after myshell starts is not a cold-start fix.
4. **Verify the actual launch contract.** After `runInstall()` writes at `src/commands/install.ts:766-790`, spawn a non-mutating interactive-shell probe with `MYSHELL_AUTOLAUNCH_PROBE=1`; the hook should emit a nonce instead of launching the TUI. Persist/return success only if the rc file that the detected shell actually sources emits that nonce. Add the probe branch to `buildHookBlock()` at `src/commands/install.ts:124-176`. This catches wrong rc targets and inherited-guard failures without a live nested TUI.
5. **Create one app-level interrupt controller with the navigation stack from Defect 2.** Add it at `src/interface/menu-navigation.ts:1 (new)` with a 1,500 ms consecutive-press window: first Ctrl+C dispatches `back` (pop one route; at root remain on root and show “Ctrl+C again to exit”), second consecutive Ctrl+C dispatches `exit`. Any accepted non-Ctrl+C input resets the sequence. Install it for the menu lifecycle at `src/interface/menu.ts:6494-6728`.
6. **Represent Ctrl+C as an event, not null.** Change `readMenuKey()` at `src/interface/menu-key-confirm.ts:190-244` to return a discriminated `MenuInputEvent` (`key`, `back`, `eof`) so Ctrl+D/EOF remain distinct from Ctrl+C. Route `back` through the controller in every menu. At `src/interface/menu.ts:7052-7055`, first Ctrl+C must no longer break the app.
7. **Make confirms cancel/back instead of killing the process.** Replace `process.kill(..., 'SIGINT')` at `src/interface/menu-key-confirm.ts:159-167` and `src/interface/menu-key-confirm.ts:301-316` with the same `back` event/result. Destructive confirmation cancellation returns to its owning route; a second consecutive Ctrl+C still exits through the app controller.
8. **Align chat/menu semantics without breaking task cancellation.** Preserve a single Ctrl+C as task cancellation while a model turn is actively running, but once idle, first press returns one route and second exits. Update `interpretInterrupt()` at `src/interface/menu-display.ts:386-410` and its handler at `src/interface/menu.ts:1599-1641` from the current three-press scheme to the shared two-press controller. Raw provider passthrough remains child-owned on the first press, but its second press should dispatch the same app exit/back result at `src/interface/menu-raw-session.ts:111-137`.
9. **Add contract tests.** Extend `test/unit/install.test.ts:130-190` to prove a new child shell with an inherited old token still launches and same-shell re-source does not. Extend `test/unit/replit-bashrc-wrapper.test.ts:84-163` for persistent shim + cold-repair verification and failed durable registration. Add menu-route tests beside `test/ui/menu-submenu-single-key.test.tsx:1`: first Ctrl+C pops exactly one level from every route; first at root stays; second consecutive exits; intervening normal input resets; Ctrl+D/EOF exits cleanly without pretending to be Ctrl+C.

#### Risk / Regression Notes

- A simple non-exported boolean is insufficiently explicit and may behave differently across shells; use an instance identifier and test bash, zsh, and PowerShell separately.
- Editing Replit project startup configuration is a meaningful mutation. It is authorized only when the user enables default-shell integration, must be marker-delimited/idempotent, and uninstall must restore the exact prior content.
- Probe mode must never launch the real TUI or write user state.
- Ctrl+C during a running task is safety-critical; do not convert the first press into navigation before aborting the active task and settling its renderer.
- Distinguish terminal EOF from Ctrl+C. EOF should close cleanly immediately; requiring two EOFs would hang automation.

#### Definition of Done

- With default shell enabled, opening a second Replit shell from an environment inheriting the first shell’s variables launches myshell exactly once.
- Re-sourcing the same rc does not double-launch; `MYSHELL_SKIP=1` always suppresses launch.
- After Replit home recreation, the durable startup adapter restores/sources the persistent hook before the first interactive prompt, without requiring a manual myshell launch. If the platform cannot provide that guarantee, Settings reports “not installed” rather than “on.”
- Install/uninstall state remains internally consistent after simulated write failures.
- From every menu depth, one Ctrl+C pops exactly one route; at root it stays and prints the second-press hint; a second consecutive press within 1,500 ms exits to the shell.
- Ctrl+C in confirms cancels/backtracks without an unhandled SIGINT, while EOF still exits immediately and an active model task is safely aborted on the first press.

## Round 2+: Broad Adversarial Audit

This is a code-read audit only. The codebase is not vaporware: it contains a real orchestration loop, bounded multi-provider execution, native-session support, verification, goals, a governor, and several unusually careful honesty seams. The product failure is integration. The normal path still exposes a procedural terminal application, while the most important “one chat” behavior is split across default-off controls, post-turn background jobs, reactive-only quota signals, and parallel decision systems that do not share one budget or one source of truth. The implementation has more machinery than the experience can justify. That is the opposite of “braindead-simple.”

### 1. Auto / Smart Mode

#### Current Reality

“Auto” is not one coherent policy. The menu calls it “Auto (smart)” (`src/interface/menu-render.ts:151-162`) and onboarding claims it chooses effort from task, risk, goals, and provider headroom (`src/interface/menu-welcome.ts:161-175`), but the actual Auto-Smart switch is explicitly default-off (`src/interface/ui/auto-smart-flag.ts:1-34`). With that switch off, the strongest detected plan kind fixes the base posture for the conversation: any Max plan selects `quality-first`, all observed Free selects `cost-saver`, and unknown/mixed plans fall to `balanced` (`src/core/policy.ts:221-239`, `src/interface/menu-auto-mode.ts:97-123`). That is subscription classification, not autonomous judgment.

There is genuine per-turn logic underneath the misleading label. The governor is enabled at the menu composition root unless explicitly disabled (`src/interface/ui/experimental-default.ts:75-121`, `src/interface/menu.ts:2644-2675`). It projects a turn into `quick`, `risky`, `decide`, `investigate`, `build`, or `explain` (`src/core/governor.ts:118-162`), then sets a 1–3-call execution budget and allocates depth, tier, panel, poll, tribunal, and verification levers (`src/core/governor.ts:677-890`). Reasoning effort is also real: it is selected from mode × admitted tier × risk/task kind and adjusted by intent confidence, engagement depth, plan-first, and fork count, then stepped down to a supported model effort (`src/core/route.ts:654-706`, `src/core/route.ts:708-751`, `src/core/route.ts:795-836`).

The automation is nevertheless blind in the exact place the product promise emphasizes: “provider headroom.” The only live pressure input is the number of providers that already produced a 429 in this conversation (`src/interface/menu.ts:1146-1169`). The code admits there is no remaining-quota readout (`src/core/capability-budget.ts:135-147`, `src/core/capability-budget.ts:207-226`), while the Control Panel literally renders quota as `unavailable in UI state` (`src/interface/ui/control-panel-model.ts:31-40`, `src/interface/ui/control-panel-model.ts:144-153`). Capacity weights are static plan-label guesses—Max 20x=10, Max 5x=4, Free=.25, otherwise mostly 1—and live load is only session token consumption divided by that weight (`src/core/capacity-allocator.ts:42-95`, `src/core/capacity-allocator.ts:243-292`).

The “get it right first time” claim is only partly real. Tests-first verification is default-on in the menu path (`src/interface/menu.ts:2677-2702`), but research-until-confident, unified preflight, model-derived risk signals, and required investigation are all default-off (`src/interface/menu.ts:3979-4021`). The brain deliberately investigates only genuinely *low* confidence, never medium (`src/core/brain.ts:197-215`, `src/core/brain.ts:740-778`). A medium-confidence implementation can therefore proceed without reading the relevant code, and ordinary implementation turns are explicitly excluded from the grounded-recommendation validator (`src/core/turn-directive.ts:656-700`, `src/core/turn-directive.ts:794-810`). “Take its time” is a gated exception; the shipped bias is still “answer unless clearly unsafe.”

#### Gap to the Vision

The UI presents one magic Auto control, but the code implements a stack of partially overlapping controls: plan-derived mode, governor allocation, auto-brain rung fusion, tier admission, capability routing, effort selection, panel/hedge presets, and feature flags. The user cannot inspect a single decision receipt explaining what Auto chose and why. Worse, the advertised headroom signal does not exist until after quota has already been wasted. A Max label can put every substantial turn in an aggressive posture even when that provider is near exhaustion; an unreported paid plan collapses to Balanced; and Free suppresses flagship use even when a second paid provider has ample capacity.

#### Highest-Leverage Fix

Create one `TurnPlan` as the sole authority for a turn. Build it after intent extraction and before any metered execution at the current governor seam (`src/core/orchestrate.ts:1795-1825`). It must contain task shape, selected provider/model/effort, total call budget, auxiliary-call budget, verification/research plan, quota evidence, fallback order, and explicit uncertainty. Replace the fixed-Auto branch at `src/interface/menu.ts:2069-2096` with this plan; make the existing auto-brain, governor, effort selector, panel/hedge, and tier-admission code consume it rather than independently re-deriving policy (`src/core/orchestrate.ts:1942-2055`, `src/core/work-call.ts:1197-1277`). Promote Auto-Smart only after this path is the default and delete the contradictory “smart” copy while it is not (`src/interface/ui/auto-smart-flag.ts:21-34`, `src/interface/menu-welcome.ts:161-175`).

Add a compact per-turn receipt to the existing trust surface: “Auto: build · Codex/5.4/high · 1 work + tests · Claude cooling 3m · no second model.” The source must be the actual `TurnPlan`, not reconstructed prose. Persist observed provider/account cooldowns and rolling consumption so the next conversation starts with evidence rather than amnesia; the current maps are born inside one chat at `src/interface/menu.ts:1065-1084`.

#### Measurable Definition of Done

- Every provider/model/effort/auxiliary call on a turn is authorized by one serialized `TurnPlan`; a test fails if any provider call lacks a plan allocation.
- “Auto” has one implementation path. No visible copy says “smart” while `autoSmartEnabled()` returns false for default config.
- The receipt’s planned call count equals the ledger’s actual call count on success, failover, review, panel, and 429 paths.
- A benchmark corpus of trivial, build, architecture, risky, and quota-pressured turns shows zero auxiliary calls on trivial turns, tests on every diff-producing turn with an available runner, and mandatory read/research before acting on every medium-or-lower confidence codebase claim.
- Routing uses persisted cooldown/consumption evidence across conversations and never describes unknown quota as headroom.

### 3. Intelligence

#### Current Reality

There is a real brain, but it is built on a brittle deterministic floor. Tier and risk start with regex tables (`src/core/classify.ts:49-81`, `src/core/classify.ts:95-149`, `src/core/classify.ts:159-218`). Any qualifying keyword evidence prevents the model router from being consulted (`src/core/classify.ts:269-289`); only the no-keyword case gets the cheapest model classifier (`src/core/route-classifier.ts:44-105`). That means a superficial word such as “review,” “plan,” “fix,” or a risk token can lock routing before semantic judgment.

The intent extractor is a real worker-model pass (`src/core/intent-extractor.ts:57-128`), but it only runs behind gates such as message length, clause count, manager tier, route plan, or partner style (`src/core/intent.ts:647-703`). Its failure silently degrades to a rules frame whose confidence is inferred from tier rather than measured understanding (`src/core/intent.ts:602-640`). Model-derived operation risk, blast radius, and freshness are deliberately stripped unless a default-off flag is enabled (`src/interface/menu.ts:3992-3999`, `src/core/orchestrate.ts:285-305`).

The higher-level brain has sound concepts—genuine forks, confidence, investigation, plan confirmation, pushback, and bounded rounds (`src/core/brain.ts:178-225`, `src/core/brain.ts:683-790`). The shipped calibration undercuts them: only measured low confidence triggers investigation (`src/core/brain.ts:197-215`), required investigation is off (`src/interface/menu.ts:4000-4012`), and web second-angle research is off (`src/interface/menu.ts:3979-3984`). The result can be intelligent when the gates happen to fire, but there is no invariant that a nontrivial code claim was grounded or that a hypothesis was verified before execution.

Planning is also downstream of action in normal chat. The auto-stage planning brain is invoked only after a successful settled turn (`src/interface/menu.ts:6362-6385`). It can therefore produce a beautiful plan for work the assistant has already attempted. On a cold cache it explicitly plans ungrounded and warms system understanding for the *next* turn (`src/interface/auto-stage.ts:499-524`). That is goal extraction, not goal-led execution.

#### Gap to the Vision

This is not merely regex wearing a costume, but regex still gets first refusal and can prevent the semantic systems from correcting it. The “brain” is a federation of classifiers, intent extraction, engagement rules, governor shape, goal planner, and output validators. Each is locally plausible; together they have no one accountable hypothesis, evidence plan, or completion contract. Staying on-task depends on prompt context and post-hoc goals rather than a turn-level objective that execution and verification share.

#### Highest-Leverage Fix

Unify route classification and intent into one structured semantic preflight. The code already has the consolidation gate, but it is default-off (`src/interface/menu.ts:3985-3991`, `src/core/orchestrate.ts:225-245`). Make that path the only model preflight for nontrivial turns; retain regex as a zero-cost floor that may constrain risk upward but may not veto semantic correction. Require the output to include objective, task shape, risk, uncertainty, evidence needed, done condition, and proposed provider/effort.

Make the goal/intent plan precede execution. Move the manager planning logic from the post-turn slot (`src/interface/menu.ts:6362-6385`) into preflight only for multi-step/substantial work, reuse its existing structured goal format (`src/core/goal-plan.ts:137-209`), and pass the chosen objective and done condition through the `TurnPlan` into verification. Turn required local investigation on for codebase claims and external research on when freshness is required (`src/core/turn-directive.ts:740-753`, `src/core/brain.ts:756-778`). Replace the “low only” rule with an evidence-sensitive rule: medium confidence can act only if the plan requires and later obtains a cheap verification signal.

#### Measurable Definition of Done

- Every nontrivial turn has one persisted objective, hypothesis/evidence plan, and done condition shared by execution and verification.
- Keyword presence cannot prevent semantic preflight from raising or lowering tier; adversarial paraphrase tests produce equivalent plans.
- Every factual codebase claim in the evaluation set cites a read file/symbol or is labeled unverified; every current/external claim has a search/source receipt.
- A 200-case corpus measures intent accuracy, risk false negatives, unnecessary questions, task drift, and verified completion; release gates are explicit rather than anecdotal.
- Auto-stage never first proposes a plan after the corresponding work has already completed.

The program spends latency on orchestration overhead before spending it on the user’s task. Mount the menu immediately from cached provider/config state, then refresh provider probes asynchronously and update Accounts/status in place. ### 5. Quota Efficiency

#### Current Reality

The code has useful failover and partial-output salvage. On an execution failure it tries an untried authenticated provider at the same tier (`src/core/work-call.ts:1853-1902`); on a rate-limit with a meaningful safe partial, it hands the draft to the next provider (`src/core/work-call.ts:1904-1945`). Multi-goal scheduling requeues 429 work with exponential backoff and a total-run ceiling (`src/core/scheduler.ts:366-370`, `src/core/scheduler.ts:540-560`, `src/core/scheduler.ts:782-845`).

The quota model still violates its own “hard budget” story. Provider failover has a separate dynamic budget—one run per authenticated provider at the tier—independent of `maxAttempts` (`src/core/work-call.ts:1867-1873`). The loop condition allows a queued failover even when `callBudgetAvailable()` is false (`src/core/work-call.ts:1197-1204`). A single failure can therefore walk every provider despite the governor’s 1–3-call budget. Conversely, timeouts are terminal and do not fail over (`src/core/policy.ts:11-16`), so the system is aggressive for explicit errors and brittle for hangs.

Cooldown is weak and local. It is a fixed five minutes (`src/core/cooldown.ts:16-32`), stored only in the current chat’s maps (`src/interface/menu.ts:1065-1084`), and if every provider is cooling the selector returns the full list and retries them anyway (`src/core/cooldown.ts:35-59`). Normal chat does not wait and resume when all capacity is exhausted; its blocked guidance says “Wait for quota refresh ... then retry” (`src/core/work-call.ts:2531-2555`). The scheduler’s wait/resume logic exists only for scheduled goals.

Multi-account capacity routing is implemented but hidden behind default-off subscription and account-parallelism gates (`src/interface/ui/subscriptions-flag.ts:5-12`, `src/interface/ui/account-parallelism-flag.ts:6-14`). Even when enabled, if all sibling accounts cool down the selector ignores cooldown and chooses one again (`src/core/opencode-account-routing.ts:35-55`, `src/core/opencode-account-routing.ts:96-105`). There is no countdown or durable wakeup state in the visible Control Panel; quota remains unavailable (`src/interface/ui/control-panel-model.ts:31-40`, `src/interface/ui/control-panel-model.ts:144-153`).

#### Gap to the Vision

Quota management is reactive, per-conversation, and retry-oriented. It cannot tell “near limit,” “hard exhausted until X,” or “transient transport failure”; it only learns after a 429. It does not provide the defining product behavior—park work, switch capacity, and resume automatically—outside `/goal`. The user is still responsible for waiting and retrying.

#### Highest-Leverage Fix

Make one persistent `CapacityState` per provider/account with observed plan, rolling tokens/calls, last error, retry-after/reset timestamp when supplied, cooldown confidence, and health. Populate it from every provider event and ledger entry at the current rate-limit callback (`src/interface/menu.ts:1678-1692`) and account selection path (`src/core/work-call.ts:1373-1476`). Replace `availableAfterCooldown()`’s all-cooling fallback with a typed `allCooling` result (`src/core/cooldown.ts:35-59`); the orchestrator should park the turn with a wake time rather than immediately retry.

Bring normal chat onto the scheduler’s bounded wait/resume primitive (`src/core/scheduler.ts:823-845`), but persist parked work so process exit/restart is safe. Count failovers, helper calls, panels, reviews, and retries against the single `TurnPlan` budget; allow a budget override only when the receipt names a newly observed provider-local failure and the user’s work would otherwise be lost (`src/core/work-call.ts:1197-1204`, `src/core/work-call.ts:1867-1945`). Promote multi-account routing only after correlated-account limits and isolation tests pass; expose real cooldown/countdown state in the Control Panel rather than fake quota percentages (`src/interface/ui/ControlPanel.tsx:121-142`).

#### Measurable Definition of Done

- No provider/account receives a call before its observed retry/reset time unless the user explicitly forces it.
- All-cooling capacity parks and automatically resumes a turn; it never immediately replays the full cooling list.
- Every metered helper, failover, panelist, synthesizer, reviewer, and planner counts against one turn budget and one receipt.
- A deterministic 429 matrix proves partial salvage, cross-provider failover, cross-account failover, process-restart resume, and no duplicate execution.
- The UI shows observed cooldown/reset countdowns and labels unknown remaining quota as unknown.

### 7. Anything in Between: Trust, Robustness, and Dead Architecture

#### Current Reality

The trust surface has an evidence-integrity bug. `makeCandidate()` passes all authenticated providers as `availableProviders` (`src/core/work-call.ts:1113-1133`). A trust receipt backed by “available means attempted” is worse than no receipt: it turns careful UI language into false evidence.

Login has another honesty failure: `runLogin()` documents and implements return code 0 even when individual authentication fails; only an invalid provider argument returns 1 (`src/commands/login.ts:302-305`, `src/commands/login.ts:389-434`). Automation cannot distinguish success from a printed failure.

That one module owns navigation, chat, goals, accounts, provider state, flags, context, quota, post-turn jobs, and rendering bridges. It contains dozens of fail-soft empty catches. Local resilience is high, but system observability is low: faults silently erase capability and the user sees a generic fallback.

Dead and contradictory architecture is accumulating. Config promises roles and level controls that change zero behavior (`src/infra/config.ts:499-519`); live wiring repeats that they are scaffolding-only (`src/interface/menu.ts:2468-2523`). The native-session header says Claude-only while the function implements Codex (`src/core/native-session.ts:12-16`, `src/core/native-session.ts:104-112`). ### MISSED findings

1. **P0 duplicate-execution risk in default-on auto-stage.** A normal chat task can complete successfully, then the fire-and-forget planner creates a semantically equivalent goal. If judged confident/adaptive, it sets that goal to `running` and invokes `spawnBackgroundGoal(created.id, title, title)` (`src/interface/menu.ts:6362-6388`; `src/interface/auto-stage.ts:598-626`). The background runner calls `runGoalLoop()` again (`src/interface/menu.ts:3848-3857`). This can repeat writes after the original task already succeeded. It directly violates “order” and “get it right first time.” Disable auto-run from post-turn auto-stage until an idempotent single-execution lifecycle exists.

2. **Source comments assert the opposite of shipped auto-stage behavior.** `menu.ts` says auto-stage is default off and “parked-only: ... never run/executed here” (`src/interface/menu.ts:3190-3198`), while the flag defaults on and the engine auto-runs (`src/interface/ui/auto-goal-flag.ts:27-47`; `src/interface/auto-stage.ts:598-626`). This is not cosmetic; it can cause reviewers and workers to preserve a nonexistent safety invariant.

3. **Verification attributes a dirty working tree to the current turn.** `verifyStage()` captures only after execution and calls `captureDiff(cwd)` without a pre-turn baseline (`src/core/work-call.ts:423-440`). The port falls back to the entire dirty working tree when no edited-file list is provided (`src/infra/verify-port.ts:60-81`). Pre-existing user changes can therefore become the “diff this turn produced,” drive tests/critic, and appear in receipts. The roadmap mentions before hashes but fails to make baseline capture a prerequisite for completion claims.

4. **Parent Accounts state is stale after child mutation.** `subs` is read once before the Accounts loop; `computeProviderAccountStates(subs)` reuses that immutable snapshot after account create/delete/re-auth (`src/interface/menu.ts:7180-7222`). The home cache is dirtied only after leaving Accounts (`src/interface/menu.ts:7317-7319`). A user can return from a child and see stale counts/status inside the same Accounts visit.

5. **The main-menu FIFO is not “small” or bounded.** The comment calls it a small FIFO, but `_menuKeyQueue.push(normalized)` has no cap (`src/interface/ui/App.tsx:225-243`, `src/interface/ui/App.tsx:743-752`). It is cleared on subflow transition, so bursts are mostly dropped rather than cross-routed, but a sustained home repaint window can grow memory and make navigation consume stale intent. A generation plus one-action/coalescing policy must be explicit.

6. **Native-session shipping truth is contradictory.** Config defaults `nativeSessions: true` (`src/infra/config.ts:633-646`), while README calls it experimental, opt-in, default off (`README.md:46-51`) and the module header claims Claude-only despite Codex support (`src/core/native-session.ts:12-20`, `src/core/native-session.ts:104-112`). The plan notices only the stale header, not the user-facing default contradiction.

7. **The audit never establishes a clean worktree baseline for its own execution plan.** This repository already had an unrelated modified `.claude/scheduled_tasks.lock`. Any delegated slice needs an explicit preserve/do-not-touch list and before/after diff receipt; otherwise evidence and rollback will be ambiguous.
