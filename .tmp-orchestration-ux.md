# myshell-tools — live orchestration display redesign

Design only (no source edits). Grounded in the actual code on `main` as of 2026-06-08.
Goal (owner's words): agent-centric counters, MEANINGFUL goal labels, multiple
stacked bottom-pinned goals each showing agent count + tokens + what it's doing,
maximum "spoon-fed" legibility — without breaking the viewport-cap / scrollback-dup
guard.

---

## 1. REALITY MAP — exactly how it works today

### (a) Where the cryptic goal label "ic" comes from

The `GoalView.label` is set in ONE place:

- `src/interface/ui/reduce.ts:225` — inside `case 'tier-start'`:
  ```ts
  const goal: GoalView = {
    id: `${action.tier}#${action.attempt}`,
    label: action.tier,          // <-- the label IS the tier string
    state: 'running',
    tokens: 0,
    agents: [agent],
  };
  ```
- `action.tier` is one of exactly three values: `src/core/types.ts:21`
  `export type Tier = 'worker' | 'ic' | 'manager';`
- The tier flows unchanged from the orchestrator's `tier-start` event
  (`src/core/orchestrate.ts:961-967`) → `coreEventToActions`
  (`src/interface/ui/core-event.ts:64-74`) → the reducer.

So **"ic" is the literal routing tier id** (Individual Contributor), not a
classification, not a truncated intent, not the user's request. The "blind"
feeling the owner saw (`◐ ic  ↓ ~0 tokens`) is exactly this: the goal card header
is `<stateGlyph> ic  ↓ ~0 tokens` (`StatusBlock.tsx:177-187`) with no human
meaning.

**What a GOOD label could be derived from (all already computed in-engine):**
- The **intent frame**: `orchestrate.ts:285-311` builds an `IntentFrame` (via
  `intentExtractor` or `rulesIntentFrame`). It has a goal/vision field already
  used to seed the work contract (`seedFromIntentAndPlan`, `orchestrate.ts:464`).
- The **work contract objective**: `WorkContract.objective`
  (`capContract({version:1, objective: task})`), and `formatGoalProgress` in
  `src/core/goal.ts:98-167` ALREADY renders `goal: <objective capped to 72 chars>`
  — proof the engine can produce a one-line human label today.
- The **user's task string** itself (cheapest, always present, zero new calls).
- The **classification.risk** (low/medium/high/critical) for a sub-label/badge.

None of these are currently threaded onto the `tier-start` CoreEvent, so the
reducer has nothing but the tier to label with. (This is the one real
orchestration change the redesign needs — see §4 Phase 2.)

### (b) What an "AGENT" actually is in myshell's model

`AgentView` (`state.ts:55-61`) = one **model attempt**: a `{provider, model,
state, tokens, attempt}`. Agents are created in two places:

1. **Sequential path** (`orchestrate.ts`, the DEFAULT path): each `tier-start`
   appends ONE `GoalView` carrying ONE `AgentView` (`reduce.ts:216-229`). A turn
   is a bounded escalation loop (`mainLoop`, `orchestrate.ts:845`) that runs
   models **one at a time**: classify → run IC → maybe cross-vendor review →
   maybe escalate to manager → accept. Each loop iteration = one provider run =
   one agent. `deps.policy.maxAttempts` bounds it. **Concurrency in the sequential
   path is ZERO** — it is strictly serial. A typical turn produces **1–3 agents
   total**, appearing one after another, not side by side.

2. **Panel path** (`ensemble.ts`, EXPERIMENTAL, `panelPolicy` default `'off'`):
   `runPanel` runs N candidates **concurrently** (`mergeCandidates`,
   `ensemble.ts:573-604`) then a synthesizer. These are represented as
   `stream.panelists` (an `AgentView[]` on the StreamView, NOT as GoalViews —
   see the H2 fix note at `reduce.ts:209-215`). Candidate count is capped:
   `cap = max(2, maxPanelProviders)` and `maxPanelProviders ?? 2`
   (`orchestrate.ts:671`, `ensemble.ts:116-117`). With three real providers
   (claude, codex, opencode) the **realistic concurrent max is 3 candidates +
   1 synthesizer**.

3. **Hedge path** (`hedge.ts`, EXPERIMENTAL, `hedgePolicy` default `'off'`):
   races a primary + ONE speculative flagship — at most **2 concurrent runs**.
   Notably hedge BUFFERS its events and only `yield*`s the WINNER's
   (`hedge.ts:177-178`, `761`), so the loser never even reaches the UI as a goal.

**Is "20 agents on one goal" real? No — it is aspirational.** The real ceilings:
- Sequential: ~1–3 sequential agents per turn (escalation depth), never parallel.
- Panel: bounded by **authenticated provider count** (≤3 today) + 1 synthesizer.
- Hedge: 2.

The hard cap on genuinely-distinct concurrent agents is **the number of
authenticated provider CLIs the user has** (claude/codex/opencode = 3). There is
no sub-agent / map-reduce / fan-out worker pool anywhere in the core. To make
"20 agents" real you would need a NEW orchestration capability (e.g. decompose a
goal into N independent sub-tasks and run them across the provider pool with a
work queue) — that does not exist and is out of scope for a display redesign.
The honest, real number to surface is **1–4**.

### (c) What `stepCount` ("29 steps") is

`stream.stepCount` (`state.ts:85`) increments by 1 on **each tool call**, and
ONLY in normal/quiet verbosity:
- `reduce.ts:279-287` `case 'stream/tool'`: `stepCount: state.stream.stepCount + 1`.
- The source is `provider-event` of `type:'tool'` (`port.ts:99`) mapped at
  `core-event.ts:80-82`. Reasoning deltas do NOT count (`reduce.ts:292-299` only
  keeps the spinner alive).

So **"29 steps" = 29 tool invocations the provider CLI made** during the current
tier (file reads, edits, shell, etc.). It is per-tier (reset at each tier-start,
`reduce.ts:48-50`) — NOT a count of agents, NOT reasoning steps. It is a real but
low-signal number to the user; "29 tool calls in tier ic" reads as noise, which
is the owner's complaint #1.

`workLabel` (`state.ts:96`) is `'Thinking'` in normal mode, or the verbose tier
label (`reduce.ts:208`). The status line renders
`⠇ Thinking… 29 steps · 51s` from `StatusLine` (`StatusBlock.tsx:259-285`).

### (d) Does the orchestrator EVER run multiple goals concurrently?

**No.** There is exactly **one goal per turn**, and turns are sequential:
- Within a turn, `goals: GoalView[]` is an array only because the sequential
  escalation loop appends a new goal per tier attempt (IC, then manager, etc.) —
  they are sequential phases of ONE user request, not parallel goals.
- `reduce.ts` `turn/start` (`reduce.ts:126-142`) RESETS `goals: []` every turn.
  So goals never persist across turns.
- The `/goal` autonomous runner (`menu.ts:1829-1900`, `goal.ts`) is also strictly
  sequential: `for (let i = 0; i < ceilings.maxIterations; i++)` runs turns one
  after another (`menu.ts:1850`), awaiting each (`runTaskWithInputHooks`,
  `menu.ts:1894`). One turn finishes before the next starts.

**Conclusion:** the owner's vision of "3 goals going, 1 goal using 20 agents,
another using 5 agents" describes a concurrent multi-goal orchestrator that
**does not exist today**. The array `goals: GoalView[]` is real but is used for
sequential tier phases of a single request. Surfacing "multiple stacked goals"
truthfully today means: stacking the **sequential tier phases** of the current
turn (IC → review → manager), which IS multiple cards, each with its agent(s).
True concurrent multi-goal requires real orchestration work (§5).

## 2. DESIGN — the redesigned, agent-centric, bottom-pinned view

### Design principles
1. **Agent count replaces step count** as the headline number. Steps (tool calls)
   become an optional dim detail, not the primary readout.
2. **Goals get human labels** from the intent/objective/task — never a bare tier.
   The tier becomes a small dim badge, not the title.
3. **A top summary line** aggregates everything in one glance:
   `▸ 1 goal · 3 agents · 1.2k tok · 51s` (counts are REAL — derived from state).
4. **Stacking is honest**: today it stacks the sequential tier-phase cards of the
   current turn; the same component scales to true concurrent goals if/when the
   orchestrator emits them. The summary line says "1 goal" when there's one.
5. **Graceful collapse** preserves the existing layout-cap contract: full cards →
   compact summary → hidden, in that order, never overflowing into scrollback.

### What is DISPLAY-ONLY vs. needs an ORCHESTRATION/STATE change

| Wow-factor | Layer | Real today? |
|---|---|---|
| Agent counter in summary + per goal | DISPLAY ONLY (`layout.ts` summary, `StatusBlock` header) — counts derive from `goal.agents` / `stream.panelists` already in state | YES — count is real (1–4) |
| Replace "N steps" with agent count on the status line | DISPLAY ONLY (`StatusBlock.tsx` `StatusLine`) | YES |
| Meaningful goal label | **STATE + ORCHESTRATION**: add a `label`/`title` field to the `tier-start` CoreEvent (or a new `goal-label` event), thread the intent/objective/task through `orchestrate.ts`/`ensemble.ts`/`hedge.ts`; map it in `core-event.ts`; store it in `reduce.ts` instead of `action.tier` | NO — needs a small engine change (the data exists, it isn't threaded) |
| Per-goal "what it's doing" one-liner | DISPLAY ONLY if we reuse `workLabel`/tool name already in `stream`; richer text needs the engine to emit a step description | PARTIAL |
| Top summary line | DISPLAY ONLY (new pure helper in `layout.ts`, rendered by `StatusBlock`) | YES |
| MULTIPLE concurrent goals each with its own agent fan-out | **ORCHESTRATION** (new concurrent multi-goal executor) | NO — aspirational |
| Stacked sequential tier-phase cards (IC→review→manager) as separate goals | DISPLAY (already multiple GoalViews) + light label change | YES |
| Tokens per goal + turn total | DISPLAY ONLY (already in `GoalView.tokens` / `tokens.turn`) | YES |
| Collapse rules under short terminal | DISPLAY ONLY (`layout.ts` already does this — extend the summary) | YES |

### The redesigned model (minimal state additions)

Add ONE optional field to `GoalView` and to the `tier-start` action/event:
```ts
interface GoalView {
  // ... existing
  readonly title?: string;   // human label: intent goal | contract objective | task (capped ~48ch)
  // label stays (tier badge); title is the headline when present, label falls back
}
```
Add a derived (no new state) **agent count** = `goal.agents.length`, and a
turn-level agent count = `Σ goal.agents.length + stream.panelists.length`.
"What it's doing" = the running agent's `workLabel`/last tool, or for panel the
existing `panelLabel`.

The summary line is a NEW pure function in `layout.ts`:
```
summarizeTurn(state) -> "▸ {nGoals} goal[s] · {nAgents} agent[s] · ↓ {tok} tok · {Ns}"
```
All four figures are real: nGoals = `goals.length` (or 1 when only stream
panelists), nAgents = the count above, tok = `tokens.turn`, Ns = injected elapsed.

## 4. IMPLEMENTATION PLAN (phased, display-first)

### Phase 1 — DISPLAY-ONLY quick wins (no engine change, biggest perceived gain)
All in the Ink view + the pure layout planner; reducer/state unchanged.

1. **Agent-count summary line.** Add pure helper to
   `src/interface/ui/layout.ts`:
   ```ts
   export function summarizeTurn(state: UiState, elapsedSecs?: number): string
   ```
   Counts: nGoals = `state.goals.length`; nAgents =
   `Σ goals[].agents.length + state.stream.panelists.length`; tok =
   `state.tokens.turn`; Ns = injected. Use "phases" when all goals share a title
   (or, pre-Phase-2, when `goals.length>1` since they share the same request).
   Render it in `StatusBlock` (`StatusBlock.tsx:376-390`) as a new 1-row line
   between `<Panels>` and `<StatusLine>`. **Budget:** add `SUMMARY_LINE_ROWS = 1`
   to the layout budget in `layoutForHeight` so the cap stays correct.

2. **Agent-centric status line.** In `StatusLine` (`StatusBlock.tsx:259-285`),
   for the non-panel branch change the verb tail from `${steps}` headline to:
   `${nAgents} agent[s] · ${stepCount} tool call[s]` (steps demoted to dim
   detail). Panel branch keeps `panelLabel` (already agent-shaped).

3. **Per-goal agent count + tidy "what it's doing".** In `GoalCard`
   (`StatusBlock.tsx:177-199`) append `· {agents.length} agent[s]` to the header
   and surface the running agent's `workLabel`/last tool as the row's activity
   text (data already on `AgentView`/`stream`). Demote the tier to a dim badge.

4. **Upgrade `compactGoalsSummary`** (`layout.ts:167-180`) to lead with the agent
   count: `2 phases · 4 agents · 1 running · ↓ 9.4k tok`.

**Tests touched:** `test/unit/ui-layout.test.ts` (new `summarizeTurn` cases +
`SUMMARY_LINE_ROWS` in the cap assertions — the planned-rows invariant
`plannedRows + inputRows <= rows` MUST still hold), `test/ui/status-block.test.tsx`
(new summary line + agent-count rendering), `npm run test:ui`, and
`npm run smoke:pty:ink` (the end-to-end PTY render must still bound-fit).

### Phase 2 — MEANINGFUL goal labels (small engine + state change)
1. **State:** add `title?: string` to `GoalView` (`state.ts:64-70`) and a
   `title?` to the `tier-start` action (`state.ts:206-213`).
2. **Engine:** thread a human label onto the `tier-start` CoreEvent. Cheapest
   truthful source already in scope at each emit site:
   - `orchestrate.ts:961` — pass the work-contract `objective`/intent goal (both
     computed just above, `orchestrate.ts:285-472`) or fall back to a capped
     `task`.
   - `ensemble.ts:714` / `:951` — pass `plan.classification`-derived objective or
     capped `task`.
   - `hedge.ts` (via `runAttempt`/`finalAndAppend`) — capped `task`.
   Add the field to the `tier-start` CoreEvent in `src/core/types.ts` and to the
   `formatGoalProgress`-style capping (reuse `goal.ts`'s `cap()` 48–72ch helper —
   extract it to a shared pure util to avoid duplication).
3. **Mapping:** `core-event.ts:64-74` copies `ev.title` → action.
4. **Reducer:** `reduce.ts:225` use `action.title ?? action.tier` for the label
   (keep `tier` as the dim badge).

**Tests touched:** `test/unit/ui-reduce.test.ts` (label now title-derived),
`test/unit/core-event.test.ts` (new field mapping), `test/unit/orchestrate.test.ts`
(tier-start carries a title), the run-stream parity test
`test/unit/run-stream-parity.test.ts` (legacy `render.ts` parity — see Risks).

### Phase 3 — richer "what it's doing" (optional engine polish)
Emit a short human step description from the engine (e.g. map a tool name like
`Bash`/`Edit`/`Read` to "running tests"/"editing files"/"reading files") rather
than the raw tool name. Pure mapping; can live in the view (`StatusBlock`) reading
the last tool from a new `stream.lastTool` field. Display-leaning; low priority.

### Phase 4 — TRUE concurrent multi-goal (large, aspirational — see §5)
Out of scope for the display redesign. Would require a new concurrent multi-goal
executor in `src/core/` that emits goals with distinct ids that persist and run in
parallel, a `goal-start`/`goal-done` CoreEvent pair, and reducer support for
goals that are NOT reset per turn. The display from Phases 1–2 already renders
this correctly the day the engine emits it (the stacking component is generic).

### Risk register
- **`render.ts` parity:** the Ink `reduce.ts` is contractually a faithful mirror
  of legacy `render.ts` (`reduce.ts:1-19`, enforced by
  `test/unit/run-stream-parity.test.ts`). Adding a `title` is additive and
  render.ts has no goal cards, so parity is about VISIBLE TEXT of prose/telemetry,
  not the goals panel — low risk, but the parity test must be re-checked.
- **Layout cap regression:** adding the summary row consumes 1 row of budget. If
  `SUMMARY_LINE_ROWS` is not subtracted in `layoutForHeight`, a borderline
  terminal could overflow → the scrollback-dup bug. The cap unit tests
  (`ui-layout.test.ts`) and `smoke:pty:ink` are the guard; add an explicit
  "summary line fits" assertion.
- **"phases" vs "goals" wording:** must NOT claim "N goals" for sequential tier
  phases of one request (dishonest count). Gate the word on shared-title.
- **Empty/zero agents:** guard `nAgents===0` (turn just started, before first
  tier-start) → summary shows `0 agents` briefly; acceptable, matches the
  existing `0 steps` behavior.
- **No new deps:** everything uses Ink + React + existing pure helpers
  (`formatTokens`, `truncateToWidth`, `pad`). Confirmed no metered services.

## 5. WHAT'S REAL vs. ASPIRATIONAL (owner honesty section)

**Real today (Phase 1–2 ships these truthfully):**
- An **agent counter** (1–4) replacing the step counter — real, derived from
  `goal.agents` + `stream.panelists`.
- **Meaningful goal labels** from the intent/objective/task — the data exists in
  the engine; Phase 2 just threads it onto the event. Small, safe change.
- A **top summary line** `▸ N goal[s]/phases · N agents · Nk tok · Ns` — every
  figure real and already in state.
- **Stacked cards** for the sequential escalation phases of the current turn
  (IC → review → manager), and for the **panel** (candidates + synthesizer) —
  this is the genuine "several agents on the screen at once" moment, and it's the
  panel/hedge experimental modes (`panelPolicy`/`hedgePolicy`) that produce it.
- **Graceful collapse** under a short terminal — already implemented in
  `layout.ts`; the redesign just makes the collapsed summary agent-led.

**Aspirational — requires REAL orchestration work, NOT display polish:**
- "**1 goal using 20 agents, another using 5 agents.**" There is no sub-agent
  fan-out, no map-reduce, no work-queue in the core. The real concurrent ceiling
  is **the number of authenticated provider CLIs (≤3) + 1 synthesizer = ~4**, and
  only in the opt-in panel mode. "20 agents" would need a new decomposition +
  concurrent-execution engine (Phase 4). Presenting a fabricated "20" would
  violate the codebase's honesty contract (e.g. `TokenMeter`'s "no fabricated
  percentages" rule, `StatusBlock.tsx:82-88`; the panel's "quota-consuming runs,
  we do NOT call it free" disclosure, `ensemble.ts:673-684`).
- **Multiple truly-concurrent GOALS** (not sequential tier phases). The
  orchestrator runs exactly one goal per turn and turns are serial (`/goal` loop
  is `for`-sequential, `menu.ts:1850`). The display will stack them honestly the
  moment a concurrent executor emits them, but the executor is the prerequisite.

**Recommended framing for the owner:** ship Phase 1 + 2 now — they deliver the
"wow, this is spoon-fed" legibility (clear labels, an agent counter, a one-glance
summary, honest stacked cards) using only display + a tiny label thread, all
within the existing viewport-cap safety. Treat "20 agents on one goal" as a
separate, larger **engine** initiative (concurrent multi-goal / sub-agent
fan-out), not a UI task — and never show an agent number the engine didn't
actually run.
