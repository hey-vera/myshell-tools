# Professional-partner turn flow: current map, the gap, and the confirm-before-execute gate

READ-ONLY research. No code changed. Repo: /home/runner/workspace (myshell-tools).

## TL;DR

- The engine ALREADY has an "understand → (reflect) → ask → execute" spine, but the only
  pre-execution interrupt it can emit is **ASK_CLARIFYING at a genuine non-investigable fork**
  (a question), NOT a **proposed plan with a confirm**. There is no "here's the plan — [y]/[edit]/[n]"
  primitive anywhere.
- "what's the plan" barrels into execution because (1) the ask path is gated on a real
  *fork* + a nonzero *fork budget* (default 0 unless `collaborative`), and (2) the new-goal seed
  (`/goal` and `runGoalLoop`) skips intent/engagement entirely and runs the loop immediately.
- The cleanest fix reuses the **TurnDirective `terminalQuestion`** seam (the existing zero-token
  pre-provider ask in orchestrate.ts §a4) + **`deriveAskFromForks`/QuestionSet** UI + the
  **EngagementPlan** decision layer. A new `proposePlan` directive field renders a confirm
  QuestionSet ([y]/[edit]/[n]) before the provider runs; on "y" we run; on "edit"/[n] we adjust.
- Decomposition into a series of goals is a **separately-designed, not-yet-built** capability
  (`docs/parallel-agent-goals-5.7.md`). Today `/goal` is a single objective + sequential loop;
  the `WorkContract.roadmap` is the decomposition substrate but the planner is design-only.

## 1. Current turn flow: user message → execution (stage by stage)

The pipeline is `orchestrate()` in `src/core/orchestrate.ts`. Each turn:

### (a) Route/classify — `orchestrate.ts:258-268`
`decideRoute(task)` → `{tier, risk, rationale}` + `decision.plan` (the latent "would a plan help?"
boolean). `routePlan` is the only signal that says "this is plan-worthy", and it only *biases*
thresholds — it never forces a confirm.

### (a2) Intent engine — `orchestrate.ts:286-320`
- `shouldExtractIntent(...)` (`intent.ts:417-437`) is the GATE. Runs the model extractor only when
  *substantial* (`routePlan` OR manager tier OR multi-clause/long) or `collaborative`. A `direct`
  non-substantial turn skips; a short worker turn skips.
- On run, `intentExtractor(task)` returns an `IntentFrame` (`intent.ts:43-61`): goal, kind,
  constraints, nonGoals, **forks** (genuine decision points, ≤3), doneWhen, confidence.
- Failure/skip → `rulesIntentFrame(...)` (`intent.ts:360-375`): deterministic, no forks, just a
  goal placeholder + kind. **The rules frame never produces forks**, so a skipped/failed turn can
  never trigger an ask.

### (a2 cont.) Engagement plan — `orchestrate.ts:313-320`, `engagement.ts:365-476`
`planEngagement(signals)` is the PURE judgment layer. It picks an ordered subset of:
`INVESTIGATE_CONTEXT, WEB_RESEARCH, REFLECT_VISION, PLAN_FIRST, DISCUSS_OPTIONS, ASK_CLARIFYING,
EXECUTE_NOW`. Key behaviors:
- **EXECUTE_NOW is the default** (`engagement.ts:461`). Thoroughness rungs are opt-in behind
  bias-shifted thresholds.
- **PLAN_FIRST** (`engagement.ts:410-413`) fires when `scopeScore >= PLAN_T(2)`. But PLAN_FIRST is
  purely **advisory prompt text** ("Produce a short plan/roadmap, then act on it" —
  `engagement.ts:582`). It does NOT stop and ask the user; the model plans *and acts in the same
  turn*. This is the closest existing thing to "propose a plan" — and it never pauses for confirm.
- **ASK_CLARIFYING** (`engagement.ts:440-446`) fires only when `realForks > 0 && hasGenuineFork`,
  AND `forkBudget(...) > 0`. `forkBudget` (`engagement.ts:330-335`) returns **0 for direct/balanced**
  and 1 only for collaborative. So even a real fork is *stated as an assumption*, not asked, unless
  the user is collaborative.
- `REFLECT_VISION` (`engagement.ts:430`) adds a one-line "reflect the goal" instruction for
  writing/design/product/planning kinds — but it's prompt text, again in the same turn, no pause.

### (a3) TurnDirective compile — `orchestrate.ts:393-401`, `turn-directive.ts:725-825`
`compileTurnDirective(...)` promotes the advisory plan into an **enforced** contract. The relevant
enforced field:
- **`terminalQuestion`** (`turn-directive.ts:809-824`): set ONLY when `plan.actions` includes
  `ASK_CLARIFYING` AND `plan.asks > 0` AND `hasGenuineFork(signals)` AND
  `deriveAskFromForks(frame, plan)` returns non-null. This is the **one existing pre-provider
  interrupt** — and it is strictly a *clarifying question at a fork*, never a plan proposal.
- Other fields: `requiredBeforeAnswer` (vision triage), `outputValidators` (generic-menu /
  grounded-recommendation), `historyPolicy` (quarantine), `workState`.

### (a4) PRE-PROVIDER TERMINAL ASK — `orchestrate.ts:504-530`
**This is the seam the new gate should reuse.** When `directive.terminalQuestion !== undefined`:
appends user entry + empty assistant entry, then `yield {type:'final', success:true, output:'',
totalCostUsd:0, questions: directive.terminalQuestion}` and RETURNS. **Zero provider attempts,
zero tokens.** The model never runs. The interface renders the QuestionSet as a selectable
multiple-choice UI (the same `ask_user` flow).

### work-contract seeding — `orchestrate.ts:457-487`
Seeds a `WorkContract` from the frame's goal/doneWhen via `seedFromIntentAndPlan`
(`engagement.ts:492-520`); a `roadmap` anchor is seeded ONLY when `plan.planFirst`. Gated by
`shouldMaterializeContract` (`work-contract.ts:233-246`: roadmap when context≠normal OR routePlan
OR manager) AND `isCleanObjectiveTask`. This is the objective/roadmap substrate — but no
decomposition into multiple goals.

### (b)–(f) execution — `orchestrate.ts:535-860+`
No-providers check, panel branch (default off), hedge branch (default off), append user message,
then the main escalation/review loop runs the provider.

### Post-turn (interface) — `menu.ts:2172-2267`
After a turn: a **timeout → "keep working autonomously?" confirm** (`menu.ts:2178-2195`), the
model's **`keep_going` offer → confirm** (`menu.ts:2203-2214`), then the post-turn slot
(question-flow selector, memory approval, queue drain). NOTE: confirms ALREADY exist here — they
use `confirm(true)` + `runGoalLoop(line)`. These are the UX precedent for a confirm-then-execute.

## 2. WHY it barrels in (the exact gap)

For "what's the plan":
1. **No fork is produced.** The intent extractor would likely return a frame with a goal like
   "understand/produce the plan" and few or zero genuine *non-investigable* forks. `hasGenuineFork`
   (`engagement.ts:293-305`) requires a vision/preference/external-decision fork; "what's the plan"
   is investigable (the partner should look at the repo). So `ASK_CLARIFYING` never selects.
2. **Even with a fork, the budget is 0.** `forkBudget` (`engagement.ts:330`) is 0 for the default
   `balanced`/`direct` style — so `plan.asks === 0`, so `terminalQuestion` is never set
   (`turn-directive.ts:809` requires `plan.asks > 0`).
3. **PLAN_FIRST doesn't pause.** Even when scope is high enough to select PLAN_FIRST, the action is
   advisory prompt text telling the model to plan *and act in one turn* — there is no
   "stop and confirm the plan" branch.
4. **The "literal goal title" symptom** comes from the goal-label/seed path: `goalTitle`
   (`orchestrate.ts:482-487`) falls back to the raw `task` ("whats the plan") when there's no
   contract objective / frame goal; and `/goal "whats the plan"` (`menu.ts:2038-2044`) seeds
   `capContract({objective: goalText})` verbatim and immediately enters `runGoalLoop` — bypassing
   intent/engagement entirely (intent is even skipped inside goalTurn, `orchestrate.ts:287-292`).

**Is confirm-before-execute gated behind a config/mode/threshold that's off by default?**
There IS no confirm-before-execute primitive at all. What exists:
- The **terminal ask** (a question, not a plan), effectively off for non-collaborative users
  because `forkBudget` defaults to 0.
- **PLAN_FIRST** (plan-and-act-in-one-turn, advisory), which is not a confirm.
- The **interface confirms** for timeout/keep_going (`menu.ts:2191,2210`) — these ARE
  confirm-then-execute, but only as *recovery/continuation* prompts, not an up-front plan proposal.

So: the machinery for "emit a structured ask before the provider runs, free, and resume on the
user's answer" is fully built and load-bearing — it's just only wired to *clarifying questions*,
and the decision layer almost never elects to use it for the default user.

## 3. Cleanest design: the "understand → propose plan → confirm → execute" gate

REUSE, don't rebuild. Three existing pieces do 90% of the work:
- **Decision layer**: `planEngagement` already computes scope/stakes/ambiguity and selects
  `PLAN_FIRST`. Add a sibling boolean it can set.
- **Enforcement seam**: `TurnDirective.terminalQuestion` + the pre-provider return
  (`orchestrate.ts:504-530`) already emits a free, structured, resumable interrupt.
- **UX/contract**: `QuestionSet` + `deriveAskFromForks` + the interface question-flow selector
  already render selectable choices and feed the answer back as the next turn's text.

### Where the gate inserts
A new directive field `proposePlan?: PlanProposal` compiled in `compileTurnDirective`
(`turn-directive.ts`), consumed in `orchestrate.ts` in a branch placed **immediately before the
existing terminalQuestion branch (a4, line 504)**. The two are mutually exclusive: a genuine fork
(`terminalQuestion`) takes precedence over a plan proposal (you ask the blocking question first).

```
// orchestrate.ts, just before line 504
if (directive.proposePlan !== undefined && directive.terminalQuestion === undefined) {
  // append user + empty assistant (carrying workTrace), then:
  yield { type:'final', success:true, output:'', tier, totalCostUsd:0,
          attempts:0, questions: directive.proposePlan.confirm };  // a QuestionSet
  return;
}
```

The `confirm` QuestionSet is a single `Question` with id e.g. `plan_confirm`, prompt = the rendered
plan summary, options `[{label:'Go'}, {label:'Edit'}, {label:'No'}]`, `allowFreeText:true` (so
"edit" can carry the user's correction as free text). This rides the EXACT `final.questions` path
already rendered by the interface — **no new UI**.

### What produces the plan text (the honesty problem)
The plan summary must be REAL, not fabricated. Two options, phased:
- **Phase 1 (shippable, bounded, zero extra model call):** the proposal is a *short, deterministic
  reflection* of the already-computed `IntentFrame` — goal + the planned engagement actions +
  doneWhen + the contract roadmap anchor if seeded. This is "I think you want X (goal), and I'd
  approach it by Y (the engagement steps). Sound good?" It is grounded entirely in the frame the
  intent extractor already produced — no second call, no hallucinated steps. This is the
  intent-frame's `goal`/`doneWhen`/`forks` rendered as a confirm rather than silently injected into
  the prompt. **This is the right first phase**: it makes the partner *reflect and confirm* using
  data it already has.
- **Phase 2 (later):** a cheap dedicated planning pass (read-only sandbox, worker/IC tier through
  the existing provider machinery) produces a concrete roadmap, then proposes it. This is exactly
  the "cheap planning pass" in `parallel-agent-goals-5.7.md §2` and should be built *with* that work,
  not before it.

### When to propose-and-confirm vs. just answer (the gating)
Add a pure predicate `shouldProposePlan(signals, plan)` in `engagement.ts`, computed alongside
`planEngagement`. It must be NARROW so a quick question never gets a confirm:
- **NEVER** when `isTrivial(signals)` (fast-path) — `engagement.ts:158`.
- **NEVER** when `plan.actions` is just `[EXECUTE_NOW]` at depth 0/1 with no PLAN_FIRST.
- **NEVER** for a `direct` partnerStyle unless irreversible (respect the user's opt-out, same as
  `forkBudget`).
- **FIRE** when the turn is genuinely build-shaped: `plan.planFirst === true` (PLAN_FIRST selected)
  OR `scopeScore(signals) >= PLAN_T` OR the directive is `substantial`
  (`turn-directive.ts:decideSubstantial`) — i.e. a multi-step build / migration / decision turn.
- **FIRE** on the irreversible+ambiguous SAFETY FLOOR (`engagement.ts:404`) — there a confirm is
  strictly safer than the current DISCUSS_OPTIONS prompt text.

This reuses the EXACT thresholds the engine already uses (`isTrivial`, `scopeScore`, `PLAN_T`,
`decideSubstantial`), so "what time is it?" and "fix this typo" stay instant, while
"build the auth system" / "what's the plan to ship X" / "migrate to Postgres" propose first.

### The confirm UX contract
- The proposal is a `final` with `questions` (the selectable selector), `totalCostUsd: 0`,
  `attempts: 0` — identical honesty posture to the terminal ask (`orchestrate.ts:519-528`).
- Options: **Go** (run now), **Edit** (free-text the correction → next turn re-runs with the edit),
  **No** (abandon / back to prompt).
- On **Go**: the next user turn is a deterministic "Confirmed: <plan>" (built like
  `formatAnswers`, `questions.ts:194`) and orchestrate runs normally — OR, for a big build, hands to
  `runGoalLoop` (the existing confirm→runGoalLoop pattern at `menu.ts:2191`). The interface decides
  which based on scope, exactly as it already does for timeout/keep_going.
- The empty assistant entry is stamped with `engineBehaviorVersion` and carries `workTrace`
  (mirror `orchestrate.ts:510-518`) so the resumed turn knows the proposed plan.

### Phasing (first phase shippable + bounded)
- **Phase 1**: `proposePlan` directive field + `shouldProposePlan` predicate + deterministic
  intent-frame-based proposal + the orchestrate branch + the interface confirm wiring (reusing
  `menu.ts` confirm precedent). Default behind a posture: ON for `collaborative`/`balanced`
  build-shaped turns, OFF for `direct` (mirrors `forkBudget` opt-out). No new model call. Fully
  unit-testable (pure predicate + pure compile + a fake-deps orchestrate test that asserts a
  proposal final with zero attempts). This alone delivers "understand → reflect → confirm → execute"
  for the default user without touching decomposition.
- **Phase 2**: dedicated cheap planning pass → concrete roadmap proposal (co-built with parallel
  goals).
- **Phase 3**: confirmed plan → multi-goal decomposition (see §4).

## 4. Connection to multi-goal decomposition

- **Today**: `/goal <text>` (`menu.ts:2038-2044`) is a **single objective**. `runGoalLoop`
  (`menu.ts:1829`) seeds `capContract({objective: goalText})` and runs ONE `buildGoalTask` →
  `orchestrate` → `parseGoalSignal` → `decideGoalNext` loop, sequentially, up to 8 turns
  (`goal.ts:56,73,296`). The model does one concrete step per turn and self-reports
  `GOAL_COMPLETE`/`GOAL_CONTINUE`.
- **The decomposition substrate exists but the planner does not.** `WorkContract.roadmap`
  (`RoadmapItem{id,text,status}`, capped to 8 by `capContract`) is the intended decomposition
  carrier. `seedFromIntentAndPlan` only seeds a single anchor item, never a real multi-item plan.
- **`docs/parallel-agent-goals-5.7.md` is the design (NOT built):** a pure DAG planner turns
  `WorkContract.roadmap` → `ParallelGoalPlan{items, waves}`, run by a coordinator above
  `orchestrate` using the `ensemble.ts` concurrency pattern. Stage 1 is read-only parallel waves;
  writes are phased (scoped → git worktrees). It explicitly preserves all gates (`authorizeTier`,
  `route()`, cooldown, ledger) and falls back to sequential `/goal`.
- **How the confirm gate connects:** the confirmed plan (Phase 2/3) becomes the seed
  `WorkContract.roadmap`, which is exactly the planner's input. So the natural build order is:
  confirm gate (Phase 1, deterministic) → planning pass produces a roadmap to confirm (Phase 2) →
  confirmed roadmap feeds the DAG planner / goal series (Phase 3, = parallel-agent-goals doc).

## 5. Honesty / subscription constraints (all respected by the design)

- **No metered API / no API keys**: Phase 1 adds ZERO model calls (deterministic proposal off the
  already-computed frame). Phase 2's planning pass uses the existing provider CLIs (OAuth
  subscription) through `orchestrate`/`route`, read-only sandbox — same as
  parallel-agent-goals-5.7 §2 mandates.
- **No embeddings / vector DB**: none introduced; the proposal is rendered from the `IntentFrame`
  and `WorkContract` already in scope.
- **Reuse provider-call machinery**: the confirm is a `final.questions` event (zero-cost), and any
  later planning/execution rides `orchestrate` + the existing route/capability/ledger/`authorizeTier`
  path. No second router, no bypass.
- **Honest costs**: the proposal final reports `totalCostUsd: 0, attempts: 0` (mirrors the existing
  terminal ask, `orchestrate.ts:519-528`).

## What's real vs. needs building

REAL (reuse as-is):
- Pre-provider zero-token structured interrupt: `orchestrate.ts:504-530` (`terminalQuestion`).
- The decision layer (`planEngagement`, `scopeScore`, `isTrivial`, `decideSubstantial`).
- `QuestionSet` + `deriveAskFromForks` + interface question-flow selector (the confirm UI).
- Interface confirm→runGoalLoop precedent: `menu.ts:2191`, `2210`.
- `WorkContract.roadmap` decomposition substrate + `seedFromIntentAndPlan`.
- `IntentFrame` (goal/doneWhen/forks/confidence) — the data for a grounded, non-fabricated proposal.

NEEDS BUILDING:
- `TurnDirective.proposePlan` field + the orchestrate branch before line 504 (Phase 1).
- `shouldProposePlan(signals, plan)` pure predicate in engagement.ts (Phase 1).
- Deterministic plan-summary renderer from the IntentFrame (Phase 1).
- Interface wiring: render the proposal confirm, on Go run / hand to runGoalLoop (Phase 1).
- Cheap planning pass → concrete roadmap (Phase 2, co-built with parallel goals).
- Multi-goal/DAG decomposition (Phase 3 = parallel-agent-goals-5.7, currently design-only).
